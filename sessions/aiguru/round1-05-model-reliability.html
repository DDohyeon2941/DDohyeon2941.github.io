Week 4 세션 요약

성과지표는 모델의 전체 데이터에 대한 평균 요약입니다.
RMSE, R², Accuracy, AUC — 모두 "전체적으로 얼마나 맞았는가"를 하나의 숫자로 압축합니다.

핵심은 이 숫자가 좋다고 해서 모델이 신뢰할 수 있다는 뜻이 아니라는 점입니다.
중요한 구간을 놓치거나, 특정 조건에서만 틀리거나, 지표 자체가 착시일 수도 있습니다.

지표가 좋아도 망하는 이유

R² 0.95, Accuracy 98% — 이 숫자들이 좋아도 실제 운영에서 문제가 생기는 경우가 있습니다.
이번 주는 그 이유를 구체적으로 다룹니다.

지표 ≠ 신뢰

지표는 "측정 가능한 범위 안에서의 요약"입니다.
측정 설계가 잘못되면, 지표가 아무리 좋아도 결과를 믿을 수 없습니다.

01 도입 — 좋은 지표가 나와도 의심해야 하는 이유 5 min
핵심 질문: Train AUC 0.99, Test AUC 0.98 — 이 모델, 배포해도 될까요?
지표가 좋아도 결과를 믿을 수 없는 4가지 경우

모델이 "잘 된다"는 착각이 생기는 이유는 대부분 다음 네 가지 중 하나입니다.

① Data Leakage — 모델이 미래 정보를 보고 학습했다. 실전에서는 그 정보가 없다.
② Bias — 학습 데이터가 현실을 왜곡해서 반영하고 있다.
③ 분포 변화 — 학습할 때와 실전 데이터의 분포가 다르다.
④ 과적합 — 학습 데이터에만 맞춰져 있어서, 새 데이터에서 망가진다.

네 가지 모두 "지표는 좋게 나왔지만 실전에서 믿을 수 없는" 상황을 만들어냅니다.

공통적인 패턴

• 학습 환경과 실전 환경이 다르다
• 데이터 설계 단계의 문제가 나중에 드러난다
• 지표만 보면 절대 발견되지 않는다
• 배포 이후에 문제가 나타나는 경우가 많다

결과를 받았을 때 자동으로 이 네 가지를 점검하는 습관

02 Data Leakage — 모델이 속임수를 썼다 15 min
핵심: 학습 시점에 사용한 정보가 실전(추론 시점)에는 존재하지 않는 경우. 지표는 좋게 나오지만 실전에서는 완전히 망가집니다.
Leakage
Data Leakage — 데이터 누수
모델이 "답지"를 보고 시험을 치른 것과 같다. 실전에서는 그 답지가 없다.
무엇인가
타겟(y)을 예측하기 위해 사용하는 특성(X) 안에
추론 시점에는 알 수 없는 정보가 포함된 상태입니다.

학습할 때는 이 정보가 있어서 성능이 잘 나오지만,
실제 운영에서는 그 정보가 없기 때문에 성능이 급락합니다.
제조에서 핵심 질문
기간계 DB든 설비 센서 데이터든,
"예측 시점 이전에 이 값을 실제로 수집할 수 있는가?"

불량 판정 코드, 검사 결과, 수리 이력 같은 값은
공정이 끝난 후에야 기간계에 기록됩니다.
이 값들이 X에 포함되어 있으면 누수입니다.

또한 개발에서 쓴 데이터와 실제 배포 파이프라인이
같은 소스를 같은 시점에 끌어오는지도 확인해야 합니다.
데이터 파이프라인이 달라지면 학습 때 없던 누수가
배포 후 생기거나, 반대로 필요한 변수가 빠질 수 있습니다.
자주 발생하는 누수 패턴
패턴 제조 예시 왜 문제인가
타겟 이후 생성 변수 불량 판정 후 입력되는 불량 코드, 검사 결과값 예측 시점에 이 값은 아직 기간계에 존재하지 않음
전처리 누수 전체 데이터로 정규화 fit 후 분리 올바른 순서: split → fit(Train) → transform(Test)
Test 통계가 정규화 기준에 섞이면 누수
설비 기준 분리 실패 설비 A 데이터를 랜덤으로 Train 70% / Test 30% 분리 설비 A의 고유 노이즈를 외운 모델 → 설비 B에 적용 불가
목적이 "범용 모델"이라면 설비 단위로 분리해야 함
타겟과 동의어 변수 수율 예측에 "공정 합격 여부(O/X)" 포함 사실상 답을 직접 주는 것과 같음
배포 파이프라인 불일치 개발 시 수동 추출 데이터 사용, 배포 시 자동화 파이프라인으로 전환 소스·시점·전처리가 달라지면 학습과 다른 데이터가 들어옴
예시 시나리오
Leakage — 가상 시나리오 공정 불량 예측 모델 — R² 0.96, 배포 후 R² 0.41
상황
반도체 공정에서 웨이퍼 수율 불량 여부를 공정 완료 전에 예측하는 모델 개발. 학습 데이터에서 R² 0.96이 나와 바로 배포를 진행했습니다.
문제
특성으로 사용한 변수 중 "최종 검사 스텝의 측정값"이 포함되어 있었습니다. 이 값은 공정이 모두 완료된 이후 측정 장비가 기간계 DB에 기록하는 값으로, 예측 시점(공정 도중)에는 존재하지 않는 정보였습니다. 개발 팀은 DB에서 데이터를 조인할 때 이 컬럼이 "공정 관련 데이터"라고 판단해 포함시켰습니다.
결과
배포 후 실시간 파이프라인에서는 해당 컬럼이 NULL로 들어왔고, 모델 성능은 R² 0.41로 급락. 해당 변수 제거 후 재학습하니 R² 0.71로 현실적인 성능이 나왔습니다.
교훈
각 변수가 기간계든 설비 데이터든, 예측 시점 이전에 실제로 수집 완료되는 값인지를 도메인 전문가와 함께 확인해야 합니다. DB 컬럼명이나 테이블 위치만으로는 판단할 수 없습니다.
Leakage 진단 체크
①
각 특성(X)이 예측 시점 이전에 실제로 수집 완료되는 값인가?
기간계 DB: 해당 레코드가 언제 INSERT/UPDATE되는지 확인
설비 데이터: 해당 센서값이 공정 어느 단계에서 기록되는지 확인
②
정규화(Scaler)를 Train 데이터로만 fit하고, Test에는 transform만 적용했는가?
올바른 순서: split → scaler.fit(X_train) → scaler.transform(X_test)
잘못된 순서: scaler.fit(X_전체) → split → transform
③
설비/라인/제품 단위 분리 목적이라면, 해당 단위로 Train/Test를 분리했는가?
범용 모델: 설비 A·B·C → Train, 설비 D → Test
랜덤 분리는 설비 고유 패턴을 외우게 만들어 신뢰할 수 없는 성능이 나옴
④
배포 파이프라인이 개발 시 사용한 데이터와 동일한 소스·시점·전처리를 따르는가?
개발 환경(수동 추출, CSV)과 배포 환경(자동화 파이프라인)이 다르면
실제로 들어오는 데이터가 달라질 수 있음. MLOps 관점에서 파이프라인 일치 여부 필수 확인
⑤
성능이 비정상적으로 좋은가? Feature importance에서 압도적인 변수가 있는가?
지나치게 좋은 성능과 특정 변수의 독주는 누수의 대표적인 신호
03 Bias — 데이터가 현실을 왜곡할 때 15 min
핵심: 모델은 학습 데이터를 기반으로만 패턴을 만듭니다. 학습 데이터가 현실을 편향되게 반영하면, 모델도 편향됩니다.
Bias
Bias — 데이터 편향
모델이 잘 학습했어도, 학습 데이터가 현실의 왜곡된 버전이라면 결과를 믿을 수 없다.
무엇인가
학습 데이터에 체계적인 왜곡이 있는 상태입니다.
특정 집단, 조건, 시기에 대한 데이터가 과소/과다 표현되어 있거나,
특정 케이스가 데이터에 애초에 포함되지 않은 경우입니다.

모델 자체의 문제가 아니라 데이터 수집 방식의 문제입니다.
왜 발견이 어려운가
편향된 데이터로 학습하고, 편향된 데이터로 평가하면
→ 지표는 좋게 나옵니다.

모델이 "학습 데이터 안에서는" 잘 작동하기 때문에
내부 지표만 보면 문제가 보이지 않습니다.

현실 데이터(실전)와 비교하거나
도메인 전문가가 검토할 때 발견됩니다.
주요 편향 유형
유형 설명 예시
생존자 편향 성공한 것만 데이터에 남는다 투자 성공 기업만 분석 → 실패 기업 패턴 누락
샘플 편향 특정 집단이 과다/과소 포함 낮 시간대 데이터만 수집 → 야간 패턴 무시
레이블 편향 정답 자체가 주관적으로 붙여짐 검사자마다 불량 기준이 다른 경우
확증 편향 기존 판단을 강화하는 방향으로만 데이터가 모임 특정 조건에서만 모니터링 → 그 조건만 데이터에 많음
예시 시나리오
Bias — 가상 시나리오 불량 예측 모델 — 주간 데이터로만 학습, 야간 공정에서 정확도 급락
상황
자동차 부품 제조사에서 용접 공정의 불량 예측 모델 개발. 6개월치 데이터를 사용했고 내부 Accuracy 91%로 양호한 성능이 나왔습니다.
문제
학습에 사용한 데이터가 주간 교대(08:00~20:00) 데이터에 집중되어 있었습니다. 야간에는 데이터 수집 시스템 오류로 로그가 제대로 쌓이지 않았고, 이를 인지하지 못한 채 모델을 개발했습니다. 야간 공정은 온도·습도 조건이 다르고 작업자 숙련도도 달랐지만, 모델은 이 패턴을 전혀 학습하지 못한 상태였습니다.
결과
주간 적용 시 Accuracy 90% 유지, 야간 적용 시 Accuracy 61%로 급락. 야간 불량을 정상으로 통과시키는 사례가 반복되면서 후공정 클레임이 증가했습니다.
교훈
전체 지표가 좋아도 교대·설비·제품 모델별로 성능을 분리해서 확인해야 합니다. 데이터가 어느 조건에서 수집됐는지를 먼저 파악하지 않으면, 모델이 커버하지 못하는 구간이 생깁니다.
실제 프로젝트 사례
실제 사례 — Coining 프로젝트 특정 호기·양산 조건으로 적용 범위를 제한한 이유
배경
Coining 공정 모델 개발 과정에서 데이터 정합성 조건을 만족하는 케이스가 전체 중 일부에 불과했습니다. 그리고 그 케이스들이 특정 제품 모델에 집중되어 있었습니다. 데이터 자체가 특정 제품 모델 위주로 편향된 상태였습니다.
판단
편향된 데이터로 학습한 모델을 전체 호기·전 제품에 범용으로 적용하면, 모델이 학습하지 못한 제품 모델과 조건에서는 신뢰할 수 없는 예측이 나올 수밖에 없습니다. 지표가 좋게 나와도 그 지표는 데이터가 있는 조건에서만 유효합니다.
결정
적용 범위를 정합성을 만족하는 데이터가 충분한 호기 및 양산 조건으로 한정했습니다. 모델이 실제로 학습한 범위 안에서만 사용하는 것입니다.
고객사 전달
이 한계를 사전에 고객사에 명확히 전달했습니다. "이 모델은 현재 데이터 기준으로 특정 조건에서 검증된 모델이며, 그 범위 밖의 제품 모델·호기에는 적용하지 않는다"는 점을 명시했습니다. 데이터가 확보되면 범위를 확장할 수 있다는 로드맵도 함께 제시했습니다.
교훈
편향된 데이터 문제를 모델 기술로 해결하려 하기보다, 모델의 적용 범위를 데이터가 실제로 커버하는 범위로 솔직하게 제한하는 것이 현실적인 대응입니다. 그리고 그 한계를 이해관계자에게 사전에 공유하는 것이 신뢰를 만드는 방법입니다.
Bias 진단 체크
①
학습 데이터는 어떻게 수집되었는가? 무엇이 빠져 있는가?
특정 조건, 기간, 집단이 과다/과소 포함되어 있지 않은지 확인
②
레이블(정답)을 누가, 어떤 기준으로 붙였는가?
검사자 또는 기준이 달라지면 레이블 자체가 일관되지 않을 수 있음
③
특정 집단 / 조건 / 시간대에서 성능이 현저히 다르지 않은가?
전체 지표가 아닌 세그먼트별 성능을 비교해야 편향이 드러남
④
도메인 전문가가 결과를 봤을 때 "말이 되는가?"
현장 상식과 크게 다른 결과가 나오면 데이터 편향을 먼저 의심
04 분포 변화 — 학습 때와 실전이 다를 때 15 min
핵심: 분포 변화는 항상 문제가 되는 건 아닙니다. 모델 성능에 실질적인 영향을 주는지가 판단 기준입니다. 영향이 크면 재학습이 필요하고, 작으면 모니터링으로 충분합니다.
Distribution Shift
Distribution Shift — 분포 변화
학습 데이터와 실전 데이터의 분포가 달라지는 것. 모델은 모르고, 지표도 모른다.
무엇인가
학습할 때의 X 분포와 실전 추론 시점의 X 분포가
달라지는 현상입니다.

제조 환경에서 주로 발생하는 원인:
• 설비 노화·교체·PM(예방정비) 이후 공정 특성 변화
• 원자재 로트 변경에 따른 입력값 분포 변화
• 계절·온습도 등 환경 조건 변화
• 제품 모델 변경 또는 공정 레시피 개정

배포 직후는 괜찮다가 시간이 지나면서 서서히 망가지는 경우가 많습니다.
성능 영향에 따라 대응이 달라진다
분포가 변했다고 해서 항상 재학습이 필요한 건 아닙니다.

성능 영향이 작은 경우
X 분포는 변했지만 X→y 관계가 유지된다면
모델 성능은 크게 달라지지 않습니다.
→ 모니터링 유지, 재학습 불필요

성능 영향이 큰 경우
공정 레시피 변경처럼 X→y 관계 자체가 바뀌면
모델이 학습한 패턴이 더 이상 유효하지 않습니다.
→ 재학습 또는 모델 교체 필요

판단 기준은 분포 변화 자체가 아니라
예측 오차가 실제로 커졌는가입니다.

개념 보충 — Covariate Shift와 Covariance
Covariate Shift 정확한 정의
두 분포의 차이를 수식으로 표현하면:

Ptrain(X) ≠ Ptest(X)
Ptrain(y | X) = Ptest(y | X)

일반적으로는 기댓값으로 표현:
Etrain[y | X] = Etest[y | X]

※ 정규분포 가정 시 예시: y ~ N(92%, σ²)
분포 형태에 따라 92%에 해당하는 값이 달라짐
(정규분포 → μ, 베타분포 → α/(α+β), 포아송 → λ)
분포를 특정하지 않으면 E[y|X]로 표현하는 것이 일반적
X 자체의 분포(평균, 분산, 범위)가 이동하지만,
X가 주어졌을 때 y가 나오는 조건부 관계 P(y|X)는 동일합니다.

여기서 "관계"는 X들 사이의 상관관계가 아니라
"X값이 주어졌을 때 y가 얼마나 나오는가"의 예측 관계입니다.

즉 X 분포 자체는 새로운 구간으로 이동했지만,
그 X값에서 y가 어떻게 나오는지의 패턴은 그대로입니다.
제조 예시
로트 변경 후 온도 센서 평균이 180°C → 195°C로 이동.
하지만 "온도가 높을수록 수율이 낮아진다"는 관계는 그대로.
→ Covariate Shift. 모델이 새 범위를 학습한 적 없어
  예측이 불안정해질 수 있지만 관계식 자체는 유효.
Covariance — 본질과 수식
두 변수 X, Y의 공분산:

Cov(X, Y) = E[(X − μX)(Y − μY)]
각 관측값이 자신의 평균에서 얼마나 벗어났는지를 곱한 기댓값입니다.

• X가 평균보다 크고 Y도 평균보다 크면 → 양수 기여
• X가 평균보다 크고 Y는 평균보다 작으면 → 음수 기여
• 이 값들의 평균 = Covariance

결국 "두 변수가 평균으로부터 같은 방향으로 움직이는가"를 측정합니다.
Covariate Shift와의 연결
분포가 이동하면 μX 자체가 바뀝니다.
같은 X값이라도 (X − μX)의 부호와 크기가 달라지고,
모델이 학습한 Covariance 구조가 실전에서 다르게 나타납니다.
→ 모델 입장에서는 "보지 못한 분포"가 됩니다.

재학습 주기 — 짧다고 좋은 게 아니다
재학습 주기를 너무 짧게 가져갈 때의 문제

분포 변화에 대응하기 위해 일 배치 등 매우 짧은 주기로
재학습하는 방식을 선택하는 경우가 있습니다.

하지만 데이터 주기가 고정되지 않으면
매번 다른 분포로 학습하는 것이 됩니다.

→ 모델이 안정적인 패턴을 학습하지 못함
→ 성능이 매일 달라져 예측 불가능한 모델이 됨
→ "학습은 되는데 성능을 기대하기 어려운" 상태

현실적인 대응 방향

① 모니터링 먼저
예측 오차, X 분포를 주기적으로 추적.
성능 저하가 감지될 때 재학습 판단.

② 재학습 주기는 도메인에 맞게
공정 변화 주기, 제품 변경 주기 기준으로 결정.
임의로 짧게 잡으면 오히려 불안정해짐.

③ 데이터 범위를 고정
재학습 시 어떤 기간의 데이터를 쓸지 기준을
명확히 정해야 재현 가능한 성능이 나옴.

분포 변화 대응 원칙
데이터를 추가한다고 성능이 보장되는 건 아니다
앞서 다룬 이유들이 그대로 적용됩니다.

• Bias가 있으면 → 데이터를 추가해도 편향된 분포가 더 강화될 뿐
• 과적합 상태라면 → 새 데이터를 섞어도 기존 패턴을 덮어쓰지 못함
• 분포 변화라면 → 새 데이터와 기존 데이터가 서로 다른 분포를 섞는 것이 되어 오히려 모델이 혼란스러워질 수 있음

데이터 추가보다 먼저 해야 할 일은 기존 모델이 어떤 케이스를 어떻게 못 맞추는지 분석하는 것입니다.
분포 변화 대응 순서

STEP 1 기존 모델의 예측 오차 패턴 분석
어떤 구간·조건에서 얼마나 틀리는가

STEP 2 분포 변화 원인 파악
변수가 바뀐 건지, X→y 관계가 바뀐 건지 구분

STEP 3 분석 완료 전까지 재학습 보류
새 데이터와 기존 데이터를 섞어 재학습하면 원인 파악이 불가능해짐

STEP 4 변화를 반영한 모델 재개발
원인이 명확해진 이후 데이터 범위·구성 결정
원칙: 분포 변화의 원인을 모르는 상태에서 새 데이터를 섞어 재학습하는 것은 문제를 덮는 것이지 해결하는 것이 아닙니다.
실제 프로젝트 사례
실제 사례 — ER 시편 삭제 프로젝트 CCL 변경 예정 상황에서의 모니터링 → 분석 → 재학습 흐름
상황
기존 모델은 특정 CCL(동박 적층판) 기준으로 학습되어 있었습니다. CCL 변경이 예정된 상황에서 기존 모델을 그대로 사용할 수 있는지, 언제부터 재학습이 필요한지를 판단해야 했습니다.
대응 ①
CCL이 변수에 포함되지 않더라도, CCL 변경 이후 전체 데이터 분포가 어떻게 달라지는지 먼저 파악하는 것을 원칙으로 잡았습니다. 기존 모델로 새 CCL 데이터를 예측했을 때 오차 패턴이 어떻게 나타나는지 모니터링을 지속했습니다.
대응 ②
분포 변화의 영향이 확인되기 전까지는 새 CCL 데이터와 기존 데이터를 섞어 재학습하지 않았습니다. 섞을 경우 기존 모델이 어떤 케이스를 왜 못 맞추는지를 분석할 기준이 사라지기 때문입니다.
대응 ③
모니터링을 통해 CCL 변경이 특정 공정 파라미터와의 관계를 실질적으로 바꾼다는 것이 확인된 이후, CCL 변경 이후 데이터를 기준으로 모델을 재개발하고 실제 적용했습니다.
교훈
변수에 직접 포함되지 않는 조건 변화라도 전체 데이터 분포에 영향을 줄 수 있습니다. 변화의 영향을 파악하기 전에 재학습을 서두르면 원인 분석의 기회를 잃습니다. 모니터링 → 분석 → 재학습의 순서를 지키는 것이 중요합니다.
예시 시나리오
Distribution Shift — 가상 시나리오 공정 수율 예측 모델 — PM 이후 성능 급락, 일 배치 재학습 도입 후 오히려 불안정
상황
디스플레이 패널 공정에서 수율 예측 모델을 6개월치 데이터로 학습. 초기 RMSE는 양호했고 3개월간 잘 작동했습니다.
문제 1
주요 증착 설비의 PM(예방정비) 이후 챔버 특성이 바뀌면서 센서값 분포가 이동했고, 동시에 온도-수율 관계도 미묘하게 달라졌습니다. 모델은 기존 패턴 그대로 예측을 냈고 RMSE가 서서히 상승했습니다.
문제 2
대응으로 일 배치 재학습을 도입했지만, 하루치 데이터만으로는 안정적인 패턴 학습이 불가능했습니다. 매일 다른 데이터 구성으로 학습하다 보니 모델 성능이 날마다 달라지는 상태가 됐고, 오히려 신뢰하기 더 어려운 모델이 됐습니다.
결과
PM 이후 데이터를 충분히 확보(2주)한 후 재학습 단 1회로 성능이 회복됐습니다. 이후 PM 이벤트를 재학습 트리거로 정의하고, 재학습 데이터 범위를 "최근 3개월"로 고정하는 정책을 수립했습니다.
교훈
재학습 주기는 짧을수록 좋은 게 아닙니다. 도메인의 변화 주기(PM, 레시피 변경, 로트 변경)에 맞춰 재학습 트리거와 데이터 범위를 함께 정의해야 안정적인 성능을 기대할 수 있습니다.
분포 변화 진단 체크
①
분포 변화가 감지됐을 때, 예측 오차도 실제로 커졌는가?
분포 이동 자체보다 성능 영향 여부가 판단 기준. 오차 증가가 없으면 당장 재학습 불필요
②
학습 데이터는 언제 수집된 데이터인가? 그 이후 설비 PM·레시피 변경·로트 변경이 있었는가?
공정 이벤트 이력과 모델 성능 이력을 함께 보면 변화 시점을 특정할 수 있음
③
재학습 주기와 데이터 범위(기간)가 명확히 정의되어 있는가?
주기가 너무 짧거나 데이터 범위가 고정되지 않으면 재학습마다 성능이 달라져 안정성을 잃음
④
배포 후 예측값 분포와 주요 X의 분포를 주기적으로 모니터링하고 있는가?
실제 y를 즉시 알기 어려운 경우, X·예측값 분포 변화로 이상을 조기 감지할 수 있음

Overfitting
Overfitting — 과적합
모델이 학습 데이터의 노이즈까지 외워서, 새 데이터에서는 일반화되지 않는 상태.
무엇인가
모델이 너무 복잡하거나, 너무 오래 학습하거나,
데이터가 너무 적을 때 발생합니다.

학습 데이터의 패턴뿐만 아니라
우연히 생긴 노이즈, 특이 케이스까지 기억합니다.

학습 데이터에서는 거의 완벽하게 맞히지만
새 데이터에는 일반화되지 않습니다.
데이터 부족 → 제품 편향
학습 데이터가 특정 제품 모델 위주라면,
모델은 사실상 "그 제품에 대한 모델"입니다.

다른 제품·라인·조건에 적용하면
성능이 크게 달라지거나 의미가 없어집니다.

과도한 일반화 기대는 위험합니다
"이 모델을 전 제품에 쓰겠다"는 기대는
데이터가 그 범위를 실제로 커버할 때만 가능합니다.
데이터가 없는 범위로의 일반화는 보장되지 않습니다.

과적합이 발생하기 쉬운 조건
데이터 관점

• 학습 데이터 샘플이 너무 적다
• 특정 제품·라인·조건에 편중된 데이터
  → 그 제품 외에는 일반화 보장 안 됨
• 특성(X) 수에 비해 샘플이 적다
• 동일한 데이터를 Train/Test에 중복 사용
• Test 기반으로 모델을 계속 수정

모델 관점

• 모델이 너무 복잡하다 (깊은 트리, 많은 뉴런)
• 정규화가 없거나 부족하다
• Cross-validation 없이 단일 분리로만 평가
• 특성 선택 없이 모든 변수를 사용

예시 시나리오
Overfitting — 가상 시나리오 설비 이상 감지 모델 — Train Accuracy 99%, 신규 설비 적용 시 Accuracy 58%
상황
화학 공장에서 반응기 설비 A 1대의 진동·온도·압력 센서 데이터 1,200건으로 이상 감지 모델 개발. Train Accuracy 99%, Test Accuracy 97%로 내부 검증은 완벽했습니다. 이 모델을 동일 사양의 설비 B·C에도 적용하기로 했습니다.
문제
설비 B·C에 적용하자 Accuracy가 58%로 급락했습니다. 분석해보니 모델이 반응기 이상 패턴이 아니라 설비 A 특유의 센서 노이즈 패턴과 진동 주기를 학습하고 있었습니다. Train과 Test 모두 설비 A의 데이터였기 때문에 내부 지표는 좋았지만, 다른 설비에는 일반화되지 않는 모델이었습니다.
결과
설비 B·C에서 실제 이상 징후를 정상으로 통과시키는 사례가 발생. 설비 A·B·C 데이터를 합산하고 설비 단위로 Train/Test를 분리해 재학습하자 Accuracy 82%로 안정화됐습니다.
교훈
단일 설비 데이터로 학습한 모델은 사실상 "그 설비 전용 모델"입니다. 여러 설비에 범용으로 쓰려면 처음부터 여러 설비의 데이터를 포함하고, 설비 단위로 평가해야 합니다.
과적합 진단 체크
①
Train vs Test 성능 차이가 크지 않은가?
RMSE 기준 20~30% 이상 차이, 분류 기준 5%p 이상 차이는 과적합 신호
②
학습 데이터 샘플 수 대비 특성 수가 많지 않은가?
샘플 100개에 특성 50개라면 과적합 가능성이 매우 높음
③
단일 Train/Test 분리가 아닌 Cross-validation을 사용했는가?
단일 분리는 운이 좋은 분리를 고를 수 있음. CV로 안정적인 평가 필요
④
Test 성능을 보면서 모델을 계속 수정하지 않았는가?
Test를 기준으로 수정을 반복하면 Test에도 과적합됨. Validation / Test 분리 필요
실무 코드 팁 Cross-validation에서 정규화 fitting 위치
❌ 잘못된 방식 — Leakage 발생
scaler = StandardScaler()
# 전체 데이터로 fit → 누수
X_scaled = scaler.fit_transform(X)

for train_idx, val_idx in kfold.split(X_scaled):
    X_train = X_scaled[train_idx]
    X_val   = X_scaled[val_idx]
    # val의 통계가 이미 scaler에 반영됨
fold를 나누기 전에 전체 X로 fit했기 때문에
val fold의 평균·표준편차가 정규화 기준에 섞임
✓ 올바른 방식 — fold 안에서 fit
for train_idx, val_idx in kfold.split(X):
    X_train = X[train_idx]
    X_val   = X[val_idx]

    scaler = StandardScaler()
    # train fold로만 fit
    X_train_s = scaler.fit_transform(X_train)
    # val에는 transform만
    X_val_s   = scaler.transform(X_val)
각 fold의 train 데이터로만 fit.
val은 transform만 → 누수 없음
Pipeline을 쓰면 자동으로 올바른 순서가 보장됩니다
sklearn.pipeline.Pipeline([('scaler', StandardScaler()), ('model', ...)])
CV 루프 안에서 Pipeline을 쓰면 매 fold마다 train으로만 fit_transform, val에 transform만 적용됩니다.

y 정의 방향 — 두 가지 목적
예측 정확도
y 값 자체를 정확히 맞추는 것이 목적
예: 다음 공정의 수율이 몇 %가 될지 예측
관심사: 예측값과 실제값의 오차가 얼마인가
주요 지표: RMSE, MAE, R² / Accuracy, AUC
해석 방향: "평균 ±2% 오차로 수율을 예측한다"

한계: 오차가 작아도, 그 예측이
실제 의사결정에 쓸 수 있는지는 별개의 문제
지표 해석 시 주의: RMSE가 낮아도 특정 구간(위험 구간)에서만 오차가 크면 운영 불가
조건 최적화
y를 원하는 범위로 오게 하는 X 조합을 찾는 것이 목적
예: 수율을 95% 이상으로 만들려면 어떤 파라미터를 어떻게 조절해야 하는가
관심사: 어떤 X 조건이 y를 목표 범위로 이끄는가
주요 지표: Feature importance, 구간별 예측 분포
해석 방향: "온도를 5도 올리면 수율이 목표 범위 안에 들어올 확률이 높아진다"

한계: 예측 오차 자체가 작지 않아도
방향성(올려야 하는지 낮춰야 하는지)이 맞으면 유용
지표 해석 시 주의: R²가 낮아도 변수 간 방향성이 안정적이면 조건 탐색에 쓸 수 있음
y 정의가 잘못되었을 때 생기는 문제
상황 실제 필요 y를 잘못 정의한 경우 결과
공정 파라미터 조정 조건 최적화 수율 값 예측 모델(예측 정확도)로 개발 RMSE는 좋지만 "어떤 조건을 바꿔야 하는지" 답을 못 줌
수율 모니터링 예측 정확도 불량/정상 분류 모델(이진 분류)로 개발 Accuracy는 높지만 수율 값의 구체적 오차를 알 수 없음
이상 감지 위험 구간 탐지 전체 평균 오차 최소화 모델로 개발 전체 RMSE는 낮지만 정작 위험 구간에서 오차가 큼
y 정의가 목적과 다를 때 지표의 함정

목적: 파라미터를 조절해서 수율을 올리고 싶다
y 정의: 수율 값 회귀 예측

→ RMSE 낮음 = 수율을 잘 예측함
→ 하지만 "무엇을 바꿔야 하는가"에 대한
   답은 이 지표에 담겨 있지 않음

지표가 좋다 ≠ 목적에 맞는 모델이다

y 정의를 먼저 확인하는 질문

① 이 모델을 만들어서 최종적으로 무엇을 하려는가?
  → 값을 예측? 조건을 찾아? 이상을 감지?

② 결과를 받은 사람이 어떤 행동을 해야 하는가?
  → 그 행동에 필요한 정보가 y에 담겨 있는가?

③ 사용할 지표가 그 목적을 평가하는 데 맞는가?
  → 예측 정확도 목적에 Feature importance가 주 지표면 어긋남

Q1. Leakage와 과적합을 어떻게 구분하는가?

둘 다 "학습에서는 잘 되는데 실전에서 망가지는" 결과를 만들지만, 원인이 다릅니다.

Leakage는 데이터 설계 문제입니다. 추론 시점에 존재하지 않는 정보가 학습에 포함된 것입니다. Train과 Test 모두 그 정보를 공유하기 때문에, Train과 Test 성능이 둘 다 높게 나옵니다. 배포 후에야 성능이 급락합니다.

과적합은 모델 학습 문제입니다. 데이터 설계는 정상이지만 모델이 Train 데이터의 노이즈까지 외운 상태입니다. Train 성능은 높고 Test 성능이 낮게 나옵니다. 배포 전에 이미 Train/Test 차이로 발견할 수 있습니다.

진단 방법: Train/Test를 둘 다 보되, 둘 다 높으면 Leakage, Train만 높으면 과적합을 먼저 의심합니다.

Q2. 이미 배포된 모델의 분포 변화를 어떻게 감지하는가?

가장 직접적인 방법은 실제 정답(y)이 쌓이는 시점에 주기적으로 성능을 재측정하는 것입니다. 하지만 많은 경우 정답을 즉시 알기 어렵습니다 (예: 이탈 여부는 한 달 후에야 알 수 있음).

이때는 두 가지 방법을 씁니다. 첫째, X의 분포를 모니터링합니다. 실전 데이터의 특성 분포가 학습 데이터와 얼마나 달라졌는지를 주기적으로 비교합니다. 평균, 분산, 최댓값 등의 변화를 추적합니다.

둘째, 예측값의 분포를 모니터링합니다. 모델이 내놓는 예측 점수나 확률의 분포가 갑자기 변한다면 입력 분포가 바뀌었다는 신호입니다. 이 두 가지를 같이 보면 정답 없이도 어느 정도 변화를 감지할 수 있습니다.

Q3. 데이터가 편향되어 있다는 걸 알면서도 그 데이터밖에 없을 때는 어떻게 하는가?

현실에서 매우 자주 발생하는 상황입니다. 이 경우 취할 수 있는 방향은 세 가지입니다.

첫째, 편향을 인지하고 결과 해석에 반영합니다. "이 모델은 A 조건에서 수집된 데이터 기반으로, B 조건에는 검증이 되지 않았습니다"라고 명시하는 것입니다. 편향 자체를 제거하지 못해도, 결과를 어디까지 신뢰할 수 있는지를 정확히 표현하는 것이 중요합니다.

둘째, 모델이 적용되는 범위를 제한합니다. 학습 데이터와 분포가 비슷한 케이스에만 모델을 적용하고, 그 범위 밖의 케이스는 별도로 처리합니다.

셋째, 추가 데이터 수집 계획을 세웁니다. 현재는 편향된 데이터를 쓰되, 부족한 집단/조건에 대한 데이터를 우선적으로 수집하는 계획을 함께 세웁니다. 모델을 배포하면서 그 데이터를 모아 나중에 재학습하는 방향입니다.

Q4. 네 가지 함정 중 실무에서 가장 자주 발생하는 것은 무엇인가?

도메인과 프로젝트 유형에 따라 다르지만, 일반적으로 가장 자주 발생하고 가장 발견이 늦은 것은 Leakage와 Bias입니다.

Leakage는 데이터를 구성할 때 각 변수의 의미를 꼼꼼히 확인하지 않으면 쉽게 발생합니다. 특히 데이터를 SQL로 뽑거나 외부 팀에서 전달받는 경우, 변수 정의를 충분히 확인하지 않아 타겟 이후 생성되는 값이 섞이는 경우가 많습니다.

Bias는 수집 과정의 구조적 문제라 개발자가 통제하기 어렵습니다. 그리고 내부 지표로는 드러나지 않기 때문에 배포 후 현장에서 "결과가 이상하다"는 피드백이 올 때까지 모르는 경우가 많습니다.

과적합은 Train/Test 분리만 제대로 해도 조기에 발견할 수 있어 상대적으로 진단이 쉽습니다. 분포 변화는 배포 후에 모니터링을 해야 발견할 수 있어 운영 체계가 없으면 뒤늦게 발견됩니다.
