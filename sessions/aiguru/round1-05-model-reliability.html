00 Last week's essentials — Week 4 Evaluation Metrics 5 min
Week 4 session summary

Performance metrics are aggregate summaries over the model's full dataset.
RMSE, R², accuracy, AUC — Each compresses "how well the model performed overall" into one number.

The key is that good numbers do not necessarily mean a trustworthy model.
The model may miss important ranges, fail under particular conditions, or benefit from misleading metrics.

Why models fail despite good metrics

R² 0.95, accuracy 98% — These numbers can look good while real operations still encounter problems.
This week examines the reasons in detail.

Metrics ≠ trust

Metrics are "summaries within the scope of what was measured."
If the measurement design is wrong, even excellent metrics cannot make the results trustworthy.

01 Introduction — Why good metrics still warrant scrutiny 5 min
Key question: Train AUC 0.99, test AUC 0.98 — Should this model be deployed?
Four situations where good metrics cannot be trusted

The illusion that a model "works well" usually comes from one of four causes.

① Data Leakage — The model learned using future information unavailable in practice.
② Bias — The training data represent a distorted version of reality.
③ Distribution shift — Training and operational data have different distributions.
④ Overfitting — The model fits only the training data and fails on new data.

All four create situations where "metrics look good, but operational results cannot be trusted."

Common patterns

• Training and operational environments differ.
• Problems originating in data design emerge later.
• Metrics alone never reveal the issue.
• Problems often appear after deployment.

Today's session goal

Build the habit of automatically checking these four issues when reviewing results.

When you hear "the metrics are good,"
→ Know which questions to ask.

02 Data leakage — The model cheated 15 min
Key point: Information available during training may not exist at inference time. Metrics look good, but the model fails completely in practice.
Leakage
Data leakage
Like taking an exam with the answer sheet. That answer sheet is unavailable in practice.
What it is
Features (X) used to predict the target (y)
contain information unavailable at inference time.

The information makes training performance look good,
but performance drops sharply when it is unavailable during operation.
The key manufacturing question
Whether using an operational database or equipment sensor data,
"Can this value actually be collected before the prediction time?"

Values such as defect classification codes, inspection results, and repair histories
are recorded in operational systems only after the process finishes.
Including these values in X creates leakage.

Also check whether development data and the deployed pipeline
retrieve the same source at the same time.
A changed pipeline can introduce leakage absent during training
or omit a required variable after deployment.
Common leakage patterns
Pattern Manufacturing example Why it is a problem
Variables created after the target Defect codes and inspection results entered after defect classification These values do not yet exist in the operational system at prediction time.
Preprocessing leakage Fit normalization on the full dataset before splitting. Correct order: split → fit(Train) → transform(Test)
Mixing test statistics into normalization creates leakage.
Failure to split by equipment Randomly split equipment A's data into 70% train / 30% test. The model memorizes equipment A's unique noise → Cannot generalize to equipment B.
For a general-purpose model, split at the equipment level.
Variables synonymous with the target Include "process pass/fail (O/X)" in yield prediction. Effectively gives the model the answer directly.
Deployment pipeline mismatch Use manually extracted development data, then switch to an automated deployment pipeline. Changed sources, timing, or preprocessing supply data unlike the training data.
Example scenario
Leakage — Hypothetical scenario Process defect prediction — R² 0.96, falling to 0.41 after deployment
Situation
A semiconductor-process model predicts whether wafer yield will be poor before completion. Training R² of 0.96 led directly to deployment.
Problem
The features included "measurements from the final inspection step". Measurement equipment records these values in the operational database only after all processing is complete; they do not exist during the process, when prediction occurs. While joining database records, the team included the column because it appeared to be "process-related data."
Result
The real-time deployed pipeline supplied NULL for this column, and R² dropped to 0.41. Removing the variable and retraining produced a realistic R² of 0.71.
Lesson
For every variable, verify whether collection is actually complete before prediction, whether it comes from an operational system or equipment with domain experts. Column names and table locations alone cannot establish this.
Leakage diagnostic checks
①
Is every feature (X) actually collected before prediction time?
Operational database: Check when each record is INSERTed/UPDATEd.
Equipment data: Check at which process stage each sensor value is recorded.
②
Was the scaler fitted only on training data, with only transform applied to test data ?
Correct: split → scaler.fit(X_train) → scaler.transform(X_test)
Incorrect: scaler.fit(X_all) → split → transform
③
If the aim is separation by equipment/line/product, was the train–test split made at that level?
General-purpose model: Equipment A, B, C → Train; equipment D → Test
A random split lets the model memorize equipment-specific patterns and produces unreliable performance.
④
Does the deployment pipeline follow the same source, timing, and preprocessing as development data?
If development (manual extraction, CSV) differs from deployment (automated pipeline),
the actual input data may change. Pipeline consistency is an essential MLOps check.
⑤
Is performance unusually good? Does one feature dominate feature importance?
Suspiciously good performance and a dominant variable are typical leakage signals.
03 Bias — When data distort reality 15 min
Key point: Models form patterns only from their training data. If the training data represent reality with bias, the model is also biased.
Bias
Bias — Data bias
Even a well-trained model cannot be trusted if its training data are a distorted version of reality.
What it is
A systematic distortion in the training data.
Some groups, conditions, or periods are underrepresented or overrepresented,
or some cases are absent from the dataset entirely.

The issue lies in how the data were collected rather than the model itself.
Why it is difficult to detect
Train and evaluate on biased data,
→ and the metrics look good.

The model works well "within the training data,"
so internal metrics alone do not reveal the problem.

It emerges when compared with real operational data
or reviewed by domain experts.
Main types of bias
Type Explanation Example
Survivorship bias Only successful cases remain in the data. Analyzing only successful investment companies → Missing patterns from failed companies
Sampling bias Some groups are overrepresented or underrepresented. Collecting only daytime data → Ignoring nighttime patterns
Label bias The ground truth is assigned subjectively. Different inspectors use different defect criteria.
Confirmation bias Data are collected only in ways that reinforce existing judgments. Monitoring only certain conditions → Those conditions dominate the data.
Example scenario
Bias — Hypothetical scenario Defect prediction — Training only on daytime data, then failing on nighttime operations
Situation
An automotive parts manufacturer developed a welding-defect prediction model. Six months of data yielded a satisfactory internal accuracy of 91%.
Problem
The training data were concentrated in daytime shifts (08:00–20:00). A nighttime data-collection system error prevented proper logging, but the team developed the model without noticing. Nighttime temperature, humidity, and operator experience differed, and the model had never learned those patterns.
Result
Daytime accuracy remained 90%, but nighttime accuracy dropped to 61%. Nighttime defects repeatedly passed as normal, increasing complaints from downstream operations.
Lesson
Even with strong overall metrics, check performance separately by shift, equipment, and product model. Unless you first understand the conditions under which data were collected, some regions will remain outside the model's coverage.
Generalized project example
Generalized example — Scope of training data Why application is restricted to validated conditions
Background
If data satisfying consistency requirements are concentrated under certain conditions, the training data may be biased.
Assessment
Predictions under unlearned conditions are difficult to trust. Interpret even strong metrics within the validated data scope.
Decision
Define the model's application scope within conditions where consistency and sufficient data have been verified.
Communicating limitations
Inform stakeholders which conditions have been validated and which have not. Consider expanding the scope when additional data become available.
Lesson
Rather than addressing bias through model techniques alone, clearly define the application scope and limitations.
Bias diagnostic checks
①
How were the training data collected? What is missing?
Check for overrepresentation or underrepresentation of conditions, periods, and groups.
②
Who assigned the labels (ground truth), and using which criteria ?
Different inspectors or criteria may make labels inconsistent.
③
Across particular groups, conditions, or times, does performance differ substantially?
Compare performance by segment, rather than relying on overall metrics, to reveal bias.
④
When domain experts see the results, "Do they make sense?"
If results depart sharply from operational knowledge, suspect data bias first.
04 Distribution shift — When training and deployment differ 15 min
Key point: Distribution shift is not always a problem. Its practical impact on model performance is the criterion. Large effects require retraining; small effects may need only monitoring.
Distribution Shift
Distribution shift
Training and operational distributions change. Neither the model nor existing metrics knows this.
What it is
The distribution of X during training differs from
the distribution of X at operational inference time.

Common causes in manufacturing:
• Process characteristics change after equipment aging, replacement, or PM (preventive maintenance).
• Input distributions change with raw-material lots.
• Environmental conditions change with seasons, temperature, or humidity.
• Product models change or process recipes are revised.

Deployment may initially work well, then gradually deteriorate over time , as it often does.
Respond according to the performance impact
A distribution change does not always require retraining.

When the performance impact is small
If the X distribution changes but the X→y relationship remains intact,
model performance changes little.
→ Continue monitoring; retraining is unnecessary.

When the performance impact is large
If the X→y relationship itself changes, as after a process-recipe revision,
the learned patterns are no longer valid.
→ Retrain or replace the model.

The criterion is not the distribution change itself,
but whether prediction errors actually increase.
Types of distribution shift
TypeDefinitionManufacturing example
Covariate Shift P(X) changes; P(y|X) remains unchanged.
The X distribution shifts, but the X→y predictive relationship stays the same.		 A material-lot change shifts sensor means while preserving their relationship with yield.
Concept Drift The X→y relationship itself changes. A recipe revision invalidates the previous temperature–yield relationship.
Label Shift The distribution of y changes. Equipment aging raises the defect rate from 0.5% to 3%.
Concept supplement — Covariate shift and covariance
The precise definition of covariate shift
Expressing the difference between two distributions mathematically:

Ptrain(X) ≠ Ptest(X)
Ptrain(y | X) = Ptest(y | X)

Usually expressed through an expected value:
Etrain[y | X] = Etest[y | X]

※ Example assuming a normal distribution: y ~ N(92%, σ²)
The parameter corresponding to 92% depends on the distribution.
(Normal → μ; beta → α/(α+β); Poisson → λ)
Without specifying a distribution, E[y|X] is the usual expression.
The distribution of X itself (mean, variance, range) shifts,
but the conditional relationship P(y|X) for a given X remains unchanged.

Here, "relationship" means the predictive relationship
"what y will be for a given X" rather than correlations among the X variables.

The X distribution moves into a new range,
but the pattern determining y at those X values stays the same.
Manufacturing example
After a lot change, mean temperature-sensor readings shift from 180°C to 195°C.
However, the relationship "higher temperature lowers yield" remains unchanged.
→ Covariate shift. The model has never learned this new range,
  so predictions may become unstable even though the underlying relationship remains valid.
Covariance — Intuition and formula
The covariance of two variables X and Y:

Cov(X, Y) = E[(X − μX)(Y − μY)]
The expected product of how far each observation deviates from its own mean.

• X above its mean and Y above its mean → Positive contribution
• X above its mean and Y below its mean → Negative contribution
• Average of these contributions = covariance

Ultimately, it measures "whether two variables move in the same direction relative to their means".
Connection to covariate shift
When the distribution shifts, μX itself changes.
Even for the same X, (X − μX) changes in sign and magnitude,
and the learned covariance structure appears differently in operation.
→ From the model's perspective, this is "an unseen distribution."
Mathematical comparison of the three types
Covariate Shift
P(X) changes; P(y|X) remains unchanged.
E[y|X] unchanged
The X distribution shifts,
but the distribution of y at fixed X stays the same.
Concept Drift
P(y|X) changes
E[y|X] changes
Even for the same X,
the distribution (expected value) of y differs.
Label Shift
P(y) changes; P(X|y) remains unchanged.
E[y] changes
The distribution of y itself shifts.
Defect prevalence/proportions themselves change.
※ Under a normal distribution, E[y|X] corresponds to μ. Other distributions express it differently, such as α/(α+β) for beta or λ for Poisson, but each denotes "the expected y at a fixed X."
Retraining frequency — Shorter is not necessarily better
Problems with retraining too frequently

To address distribution shifts, teams sometimes choose
very frequent retraining, such as daily batches.

However, without a fixed data window,
each run learns from a different distribution.

→ The model cannot learn stable patterns.
→ Performance changes daily and becomes unpredictable.
→ "Training works, but dependable performance is difficult to expect."

Practical response

① Monitor first
Track prediction errors and X distributions regularly.
Consider retraining when performance degradation is detected.

② Match retraining frequency to the domain
Base it on process-change and product-change cycles.
Arbitrarily short cycles can make the model less stable.

③ Fix the data window
Clearly define which period's data
will be used in retraining to obtain reproducible performance.

Principles for responding to distribution shift
Adding data does not guarantee better performance.
The reasons discussed earlier still apply.

• Bias is present → More data only reinforce the biased distribution.
• Overfitting is present → Mixing new data may fail to replace the learned patterns.
• Distribution shift is present → Combining new and old data mixes distributions and may confuse the model further.

Before adding data, analyze which cases the existing model misses and how it fails.
Response sequence for distribution shift

STEP 1 Analyze the existing model's prediction-error patterns.
Which ranges and conditions fail, and by how much?

STEP 2 Identify the cause of the distribution change.
Distinguish changes in variables from changes in the X→y relationship.

STEP 3 Hold retraining until the analysis is complete.
Mixing old and new data for retraining obscures the cause.

STEP 4 Redevelop the model to reflect the change.
Determine the data window and composition after establishing the cause.
Principle: Mixing new data and retraining before understanding the shift conceals the problem rather than solving it.
Generalized project example
Generalized example — Responding to changed operating conditions Monitoring → Analysis → Retraining when conditions change
Situation
A model learned from data under particular operating conditions. When those conditions change, determine whether the existing model remains applicable and when retraining is needed.
Response ①
Even if the changed condition is not an explicit feature, first examine how the overall data distribution changes. Monitor the existing model's prediction-error patterns on data collected under the new conditions.
Response ②
Until the effect of the distribution shift is established, keep data from the new conditions separate from the old data for retraining. Mixing them removes the reference needed to analyze which cases the existing model misses and why.
Response ③
After monitoring confirms that the changed conditions materially affect relationships among the data, use data from the changed conditions to reassess and rebuild the model.
Lesson
A condition change can affect the overall data distribution even when it is not an explicit model feature. Rushing to retrain before understanding its effects loses the opportunity to analyze the cause. Follow the order: monitoring → analysis → retraining.
Example scenario
Distribution shift — Hypothetical scenario Yield prediction — Performance falls after PM; daily retraining makes it less stable
Situation
A display-panel yield model trained on six months of data initially achieved satisfactory RMSE and worked well for three months.
Problem 1
After PM (preventive maintenance) on major deposition equipment, chamber characteristics changed, shifting sensor distributions and slightly changing the temperature–yield relationship. The model continued using old patterns, and RMSE rose gradually.
Problem 2
Daily batch retraining was introduced, but one day's data could not support stable pattern learning. Training on a different data composition every day made daily performance vary and the model even harder to trust.
Result
After sufficient post-PM data were collected (2 weeks), one retraining run restored performance. PM events were then defined as retraining triggers, with the training-data window fixed at "the most recent 3 months."
Lesson
Shorter retraining cycles are not necessarily better. Define retraining triggers and data windows together, aligned with domain change cycles (PM, recipe revisions, lot changes) to obtain stable performance.
Distribution-shift diagnostic checks
①
When a distribution change is detected, have prediction errors actually increased?
Judge by performance impact, not the shift alone. If errors have not increased, immediate retraining is unnecessary.
②
When were the training data collected? Has equipment PM, a recipe revision, or a lot change occurred since then?
Compare process-event histories and model-performance histories to identify when the change occurred.
③
Are retraining frequency and the data window clearly defined?
Overly short cycles or unfixed data windows cause performance to vary with each retraining and undermine stability.
④
After deployment, are prediction distributions and key X distributions monitored regularly?
If actual y is not immediately available, changes in X and prediction distributions can provide early warning.
05 Overfitting — Memorizing only the training data 15 min
Connection to Week 1: We briefly covered overfitting in the linear-model session. Here we revisit it through "good metrics, poor operational performance."
Overfitting
Overfitting
A model memorizes even training-data noise and fails to generalize to new data.
What it is
It occurs when a model is too complex, trains too long,
or has too little data.

It remembers not only the training-data patterns
but also chance noise and unusual cases.

Training predictions are almost perfect,
but do not generalize to new data.
Insufficient data → Product-specific bias
If most training data come from a particular product model,
the model is effectively "a model for that product".

On other products, lines, or conditions,
its performance can change sharply or become meaningless.

Excessive expectations of generalization are dangerous.
"We will use this model for all products"
is realistic only when the data actually cover that scope.
Generalization to regions without data is not guaranteed.
Diagnosing with the train–test gap
Normal

Train RMSE 2.1
Test RMSE 2.4
→ Small gap

Overfitting signal

Train RMSE 0.3
Test RMSE 3.8
→ Large gap

Severe overfitting

Train Acc 99%
Test Acc 61%
→ Immediate inspection needed

Conditions prone to overfitting
Data perspective

• Too few training samples
• Data concentrated in particular products, lines, or conditions
  → No guaranteed generalization beyond those products
• Few samples relative to the number of features (X)
• The same data duplicated in training and test sets
• Repeated model adjustments based on test results

Model perspective

• Excessive complexity (deep trees, many neurons)
• Missing or insufficient regularization
• Evaluation on one split without cross-validation
• All variables included without feature selection

Example scenario
Overfitting — Hypothetical scenario Equipment anomaly detection — Training accuracy 99%, dropping to 58% on new equipment
Situation
A chemical plant built an anomaly model from 1,200 vibration, temperature, and pressure records from one reactor, equipment A. Training accuracy was 99% and test accuracy 97%, making internal validation look excellent. The model was then selected for equipment B and C with identical specifications.
Problem
Accuracy fell to 58% on equipment B and C. Analysis showed that the model had learned equipment A's sensor-noise patterns and vibration cycles rather than reactor anomaly patterns. Both train and test data came from A, so internal metrics were strong, but the model did not generalize to other equipment.
Result
Actual anomalies on B and C passed as normal. Combining data from A, B, and C and retraining with equipment-level train–test splits stabilized accuracy at 82%.
Lesson
A model trained on one machine is effectively "a model dedicated to that machine". General-purpose use across machines requires data from multiple machines and equipment-level evaluation from the outset.
Overfitting diagnostic checks
①
Is the train–test performance gap large?
An RMSE gap of 20–30% or more, or a classification gap of at least 5 percentage points, signals overfitting.
②
Do the training data have too many features relative to the sample size?
With 100 samples and 50 features, the risk of overfitting is very high.
③
Did you use Cross-validation rather than just one train–test split?
A single split may be lucky. Cross-validation is needed for stable evaluation.
④
Did you repeatedly modify the model while watching test performance?
Repeated test-based adjustments overfit the test set too. Keep validation and test sets separate.
Practical code tip Where to fit normalization in cross-validation
❌ Incorrect — Creates leakage
scaler = StandardScaler()
# Fit on the full dataset → Leakage
X_scaled = scaler.fit_transform(X)

for train_idx, val_idx in kfold.split(X_scaled):
    X_train = X_scaled[train_idx]
    X_val   = X_scaled[val_idx]
    # Validation statistics have already entered the scaler
Fitting on all X before splitting folds
mixes validation-fold means and standard deviations into normalization.
✓ Correct — Fit inside each fold
for train_idx, val_idx in kfold.split(X):
    X_train = X[train_idx]
    X_val   = X[val_idx]

    scaler = StandardScaler()
    # Fit only on the training fold
    X_train_s = scaler.fit_transform(X_train)
    # Only transform validation data
    X_val_s   = scaler.transform(X_val)
Fit only on each fold's training data.
Only transform the validation data → No leakage
A Pipeline automatically ensures the correct sequence.
sklearn.pipeline.Pipeline([('scaler', StandardScaler()), ('model', ...)])
Inside a cross-validation loop, a Pipeline applies fit_transform only to training data and transform to validation data in each fold.
05b Before interpreting metrics — How was y defined? 10 min
Key question: What is the model designed to predict well? Does that purpose match the current need?
Change the definition of y, and everything changes.

Even with the same data and model, how y is defined
completely changes the objective, metrics, and interpretation of results.

Before saying "the model performs well," check which definition of y it performs well against.

Two purposes for defining y
Prediction accuracy
The aim is to predict the value of y accurately.
Example: Predict the next process's yield percentage.
Focus: How large is the error between predicted and actual values?
Main metrics: RMSE, MAE, R² / Accuracy, AUC
Interpretation: "Yield is predicted with an average error of ±2%."

Limitations: Even a small error does not establish whether the prediction
supports real decisions.
Metric caution: Low RMSE does not make a model operationally usable if errors remain large in a particular high-risk range.
Condition optimization
The aim is to find combinations of X that place y in the desired range.
Example: Which parameters should be adjusted, and how, to achieve yield of at least 95%?
Focus: Which X conditions lead y into the target range?
Main metrics: Feature importance, prediction distributions by range
Interpretation: "Increasing temperature by 5 degrees raises the probability that yield falls within the target range."

Limitations: Even if prediction error is not very small,
correct directionality (whether to increase or decrease a setting) can be useful.
Metric caution: Even with low R², stable directional relationships among variables may support condition exploration.
Problems caused by a poorly defined y
Situation Actual need Incorrect definition of y Result
Adjust process parameters Condition optimization Build a yield-value prediction model (prediction accuracy). Good RMSE cannot answer "Which conditions should change?"
Monitor yield Prediction accuracy Build a defective/normal classifier (binary classification). High accuracy does not reveal the specific error in yield values.
Anomaly detection Detect high-risk ranges Build a model minimizing overall average error. Overall RMSE is low, but errors are large precisely in the high-risk range.
The metric trap when y differs from the purpose

Goal: Increase yield by adjusting parameters.
Definition of y: Regression prediction of yield values.

→ Low RMSE = good yield prediction.
→ However, the metric does not answer
   "What should we change?"

Good metrics ≠ a model suited to the purpose

Questions to check the definition of y first

① What do we ultimately want to accomplish by building this model?
  → Predict a value? Find conditions? Detect anomalies?

② What action should the person receiving the results take?
  → Does y contain the information needed for that action?

③ Is the chosen metric appropriate for evaluating that purpose?
  → Feature importance as the main metric for prediction accuracy is a mismatch.

06 Diagnostic checklist — What to question, and in what order 10 min
Goal: Questions to ask automatically when you hear "The model's performance is good."
Before finalizing metrics — Discuss with business stakeholders
Evaluation metrics can be adjusted through discussion.
Metric criteria (thresholds, acceptable error ranges, etc.) can be adjusted to balance strong numerical performance with practical usability.
For a useful discussion, however, first understand which factors affect the metrics and how.
Discussion point ①
Set acceptable error ranges
At what RMSE can stakeholders actually use the model?
First ask, "Can operational decisions be made with ±5% error?" Then set the metric target accordingly.
Discussion point ②
Balance false positives and false negatives
Which is more costly: missing a defect or flagging a normal item as defective?
Adjust the threshold to the operational cost structure.
Discussion point ③
Reflect the importance of different ranges
Require separate performance for important ranges (high-risk regions, key product models), rather than only overall average error.
Include these requirements in metric design in advance.
For a productive discussion,
understand that
• Leakage → Inflated metrics make discussion criteria meaningless.
• Bias → Poor performance under specific conditions undermines an overall agreement.
• Overfitting → The current metrics will not reproduce in operation.
Discussion sequence
1. Check the four pitfalls first → Verify that metrics are trustworthy.
2. Understand the operational context → Which errors are more critical?
3. Agree on metric criteria → Finalize numerical targets and acceptable ranges.

Check the definition of y before interpreting metrics
□ Is this model intended for Prediction accuracy or Condition optimization?
□ Is y defined for that purpose? Is regression, classification, or range detection needed?
□ Are the current metrics (RMSE, accuracy, etc.) appropriate for evaluating that purpose?

Diagnose the four pitfalls in sequence
When pitfalls overlap

The four pitfalls can occur simultaneously.

Example: Training on biased data + overfitting the training data
Example: Leakage while the distribution has already changed

Finding one does not rule out the others.

Why metrics alone are insufficient

All four are difficult to detect through internal metrics alone.

• Leakage → Metrics are unusually good.
• Bias → Invisible when evaluation uses only internal data.
• Distribution shift → Appears only after deployment.
• Overfitting → Invisible from training performance alone.

Step-by-step diagnostic flow
1
Check data leakage first — Be more skeptical when metrics look better
□ Is each feature actually knowable at inference time?
□ Was preprocessing performed on the full dataset before the train–test split?
□ Is performance unusually high relative to the problem's difficulty?
□ Does one variable dominate importance? What exactly does it mean?
2
Check bias — Trace the data-collection process
□ How, when, and by whom were the training data collected?
□ Are some groups, conditions, or times overrepresented or underrepresented?
□ Who assigned the labels, and using which criteria?
□ Does performance differ by segment? Check ranges rather than only overall metrics.
3
Check distribution shift — Compare training and operational periods
□ When were the training data collected? How different are conditions now?
□ Are key operational feature distributions similar to those in training?
□ Have prediction errors increased over time after deployment?
□ Have structural environmental changes occurred (policies, systems, external events)?
4
Check overfitting — Measure the train–test gap
□ How large is the train–test gap? (RMSE difference ≥ 20%, accuracy difference ≥ 5 percentage points → Caution)
□ Was cross-validation used, or just one split?
□ Are there too many features relative to the sample size?
□ Was the model repeatedly modified while monitoring test performance?

07 Q&A 10 min
Discuss questions raised during the session or the anticipated questions below.
Q1. How do we distinguish leakage from overfitting?

Both produce "good training results but operational failure," but their causes differ.

Leakage is a data-design problem. Training includes information unavailable at inference time. Both train and test sets share it, so both show high performance. Performance falls only after deployment.

Overfitting is a model-learning problem. Data design is sound, but the model memorizes training noise. Training performance is high and test performance low. The train–test gap can expose it before deployment.

Diagnosis: Examine both train and test. If both are high, suspect leakage first; if only training is high, suspect overfitting first.

Q2. How can distribution shift be detected in an already deployed model?

The most direct approach is to remeasure performance regularly as ground truth (y) arrives. However, ground truth often becomes available only later (e.g., churn is known a month afterward).

Use two approaches in that case. First, monitor the distribution of X. Periodically compare operational feature distributions with training distributions. Track changes in means, variances, maxima, and similar statistics.

Second, monitor prediction distributions. A sudden change in model scores or probabilities signals changed input distributions. Together, these checks can detect some shifts even without ground truth.

Q3. What if we know the data are biased but have no other data?

This is common in practice. There are three possible responses.

First, acknowledge the bias in interpreting results. State, "This model is based on data collected under condition A and has not been validated under condition B." Even if bias cannot be removed, clearly communicate the scope of trust.

Second, restrict the model's application scope. Apply it only where distributions resemble the training data, and handle cases outside that scope separately.

Third, plan additional data collection. Use the available biased data for now, while prioritizing collection from underrepresented groups and conditions. Collect those data during deployment and retrain later.

Q4. Which of the four pitfalls occurs most often in practice?

It depends on the domain and project, but the most common and latest to be detected are generally leakage and bias.rather than the model itself.

Leakage arises easily unless each variable's meaning is checked during data preparation. With SQL extracts or data from another team, insufficient definition checks often let post-target values enter the dataset.

Bias is a structural collection problem that developers may struggle to control. Internal metrics do not reveal it, so it may remain unnoticed until operational users report "the results are strange" after deployment.

Overfitting is relatively easy to diagnose early with a proper train–test split. Distribution shift requires post-deployment monitoring and may be detected late without an operational monitoring process.
