클러스터링은 정답을 주지 않습니다. 데이터를 나눠줄 뿐입니다.
그 나눔이 의미 있는지 판단하는 건 알고리즘이 아니라 사람의 몫입니다.

군집 결과가 나왔을 때 올바른 보고 방식:
❌ "군집 1이 위험 군집입니다"
✅ "고온·고압·저유량 조건에서 불량률이 높게 나타나는 패턴을 발견했고, 이 조건을 모니터링 기준으로 활용할 수 있습니다"

인과 ≠ 상관

클러스터링이 찾은 건 "이 조건에서 불량이 많았다"는 패턴. "이 조건이 불량을 만든다"는 원인이 아닙니다. 이번 주 지표도 동일합니다 — 숫자가 좋다고 모델이 옳은 건 아닙니다.

도메인 검증 필수

결과에 이름을 붙일 수 있는지, 현장에서 말이 되는지 항상 검증해야 합니다. 지표가 아무리 좋아도 현장 맥락과 맞지 않으면 신뢰할 수 없습니다.

01 지표를 보는 관점 — "평균 성적표"의 함정 5 min
핵심 질문: 모델이 "전체적으로" 잘 맞는 것과 "중요한 구간에서" 잘 맞는 것은 다릅니다. 지표는 어느 쪽을 보여주는가?
지표 = 전체 데이터의 평균 요약

RMSE 1.2, Accuracy 97%, AUC 0.93 — 이 숫자들은 모두 전체 데이터에 걸친 평균입니다.

문제는 제조 현장에서 중요한 건 "전체 평균"이 아닌 경우가 많다는 겁니다.

불량률 0.5% 공정에서 불량 케이스 50개를 다 놓쳐도 → 정상 9950개를 맞히면 Accuracy 99.5%
수율 예측에서 정상 구간(85~95%)은 잘 맞추지만 → 위험 구간(60% 이하)은 체계적으로 틀려도 R² 0.92

지표 하나로 결론 내리면 안 되는 이유

지표가 좋아도 잘못된 경우:
• 중요한 소수 케이스(불량)를 체계적으로 놓침
• 특정 공정 조건 구간에서만 틀림
• 학습 데이터 누수로 인한 착시
• 공정 조건이 바뀐 데이터에 적용

지표를 제대로 쓰는 방법

지표를 시작점으로 쓰되:
• 어느 구간에서 오차가 큰지 잔차 확인
• 불량 케이스만 따로 성능 측정
• Train vs Test 차이 얼마인지 확인
• 현업 기준(Cpk, 스펙 한계)과 비교

02 회귀 지표 — MAE / RMSE / R² / Adjusted R² 15 min
공통 시나리오: 공정 수율(%) 예측 모델. y = 실제 수율, ŷ = 예측 수율. 정상 범위 85~95%, 위험 구간 70% 이하
MAE
Mean Absolute Error — 평균 절대 오차
오차의 절댓값 평균. 단위가 y와 같다. 이상치에 둔감하다.
수식
MAE = (1/n) × Σ|y - ŷ|
예측값이 평균적으로 얼마나 빗나가는지 직관적으로 보여줍니다.
수율 예측 MAE = 2.1% → "평균적으로 ±2.1% 오차가 난다"
제조 해석
장점: 오차 크기를 현업이 바로 이해 가능
"MAE 2%면 수율 예측이 평균 2% 빗나간다" — 직관적

한계: 큰 오차와 작은 오차를 동일한 비중으로 봄
수율 90%를 92%로 예측한 오차(2%)와
수율 60%를 62%로 예측한 오차(2%)를 같게 취급
✓ 적합한 경우
이상치가 많거나 극값이 중요하지 않을 때. 현업에게 오차 크기를 설명할 때
! 주의
큰 오차가 치명적인 상황(불량 감지, 위험 구간 예측)에서는 RMSE를 함께 봐야 함
RMSE
Root Mean Squared Error — 평균 제곱근 오차
오차 제곱의 평균에 루트. 큰 오차에 더 민감하다. 단위는 y와 같다.
수식
RMSE = √((1/n) × Σ(y - ŷ)²)
오차를 제곱하기 때문에 큰 오차 하나가 RMSE를 크게 끌어올립니다.
MAE보다 항상 크거나 같습니다 (RMSE ≥ MAE).
MAE vs RMSE — 차이
오차가 [1, 1, 1, 1, 10] 이라면:
→ MAE = (1+1+1+1+10)/5 = 2.8
→ RMSE = √((1+1+1+1+100)/5) = 4.6

큰 오차 하나(10)가 RMSE를 크게 키웁니다.
RMSE ≫ MAE이면 → 큰 오차가 간헐적으로 발생한다는 신호
✓ 적합한 경우
큰 오차가 치명적인 상황. 위험 구간 예측, 설비 이상 감지에서 큰 빗나감을 벌칙으로 줘야 할 때
✕ 주의
이상치 데이터가 오염된 경우 RMSE가 이상치에 끌려다닐 수 있음. 데이터 품질 먼저 확인
R²
R-squared — 결정계수
모델이 y의 분산을 얼마나 설명하는가. 0~1 (음수도 가능). 단위 없음.
수식
R² = 1 - SS_res / SS_tot

SS_res = Σ(y - ŷ)² ← 모델 오차
SS_tot = Σ(y - ȳ)² ← 전체 분산
R² = 1.0 → 완벽한 예측
R² = 0.0 → 평균값만 예측하는 것과 같음
R² < 0.0 → 평균값보다도 못한 예측 (가능함!)
R² 함정 3가지
① 변수를 추가할수록 R²은 무조건 오른다
쓸모없는 변수를 넣어도 R²은 절대 떨어지지 않음
→ 이유는 아래 박스 참고

② 음수가 나올 수 있다
train 범위 밖 데이터에 적용하면 음수 R² 가능

③ 구간 편향을 숨긴다
정상 구간에서 잘 맞고 위험 구간에서 틀려도
전체 R² 0.95가 나올 수 있음
! R² 0.9x를 볼 때 반드시 확인
잔차 플롯에서 수율 위험 구간(70% 이하)의 오차는 얼마인가? 그 구간만 따로 RMSE를 계산해보면 전혀 다른 그림이 나올 수 있음
✕ 주의
변수 개수가 다른 모델끼리 R²로만 비교하면 안 됨 → Adjusted R² 필요
왜 변수를 추가하면 R²이 무조건 오르는가 — 본질

모델에 변수를 하나 추가하면 모델 입장에서 선택지는 두 가지입니다.

이 변수가 유용하면 → 써서 오차를 줄인다 → R² 오름
이 변수가 쓸모없으면 → 계수를 0에 가깝게 만들어서 사실상 무시한다 → R² 그대로

두 경우 모두 R²는 내려가지 않습니다. 최악의 경우 제자리입니다.
즉 변수를 추가하는 것은 모델에게 "더 잘할 기회"를 주는 것이지, "더 잘해야 할 의무"를 주는 게 아닙니다.

문제는 "우연히 발견한 패턴"입니다.
수율과 무관한 변수(예: 작업자 사번 뒷자리, 측정 순서 번호)를 25개 추가하면
모델이 훈련 데이터에서만 존재하는 우연한 패턴을 학습합니다.
→ 훈련 데이터 R² = 0.91 (올라감)
→ 새 데이터 R² = 0.74 (오히려 떨어짐)

R²만 보고 "변수를 더 넣을수록 좋다"고 판단하면 과적합으로 이어집니다.
변수를 추가할 때는 반드시 Test R²와 Adjusted R²를 함께 봐야 합니다.

Adj R²
Adjusted R² — 수정 결정계수
변수 개수에 대한 패널티를 반영한 R². 모델 간 공정한 비교.
수식 — 어떻게 보완하는가
Adj R² = 1 - SS_res / (n-p-1)
────────────────
SS_tot / (n-1)

n = 샘플 수 / p = 변수 개수
R²와 차이는 하나입니다.
SS_res를 (n-p-1)로 나눕니다.

변수(p)가 늘면 → (n-p-1)이 작아짐
→ SS_res/(n-p-1)이 커짐
→ Adj R²가 내려감

변수 추가의 이득(SS_res 감소)이
패널티(n-p-1 감소)보다 작으면
Adj R²는 내려갑니다.
수치 예시
모델 A: 변수 5개, R² = 0.88, Adj R² = 0.87
모델 B: 변수 30개, R² = 0.91, Adj R² = 0.84

R²만 보면 B가 좋아보입니다.
Adj R²로 보면 A가 더 낫습니다.

B는 변수 25개를 추가해서 R² 0.03을 올렸지만,
실제 설명력 증가보다 패널티가 더 컸다는 뜻입니다.

Adj R²가 내려갔다 = 방금 추가한 변수가
모델에 실질적 도움이 안 됐다는 신호
✓ 사용 상황
변수 개수가 다른 모델끼리 비교. 센서가 많은 제조 데이터에서 변수 선택할 때 참고 지표로 활용
✕ 한계 — 패널티가 정확하지 않다
(n-p-1) 보정은 자유도 기반 추정값입니다. "변수 1개 = 정확히 이만큼 패널티"가 현실에서 항상 맞지 않습니다. 변수 간 상관이 높거나 n이 작으면 불안정합니다. → 더 신뢰할 수 있는 방법은 Train/Test 분리 또는 Cross-Validation으로 직접 측정하는 것
(n-p-1)의 근거 — 방정식, OLS, 자유도

Step 1 — 방정식이란
"모르는 값(미지수)을 포함한 등식"입니다.
미지수를 알아내려면 방정식이 미지수 수만큼 있어야 합니다.

Step 2 — 데이터 1개 = 방정식 1개
변수 2개짜리 모델: 수율 = a×온도 + b×압력 + c
미지수 a, b, c — 3개

데이터 1개(온도=85, 압력=3.2, 수율=91)를 넣으면:
91 = a×85 + b×3.2 + c
숫자가 확정되고 a, b, c만 모릅니다 → 방정식 1개
데이터가 1개 추가될 때마다 방정식이 1개씩 생깁니다.

Step 3 — 방정식 수와 미지수 수의 관계
방정식 < 미지수 → 해가 무한히 많음 (모델 성립 안 됨)
방정식 = 미지수 → 해가 딱 하나 → SS_res = 0 → 데이터를 외운 것
방정식 > 미지수 → 완벽한 해가 없음 → 잔차 발생 → 진짜 오차 측정 가능

회귀에서는 항상 세 번째 경우를 원합니다.
데이터 100개, 미지수 3개 → 100개 방정식을 동시에 만족하는 해가 없음
→ OLS가 "잔차 제곱합을 가장 작게 하는 a, b, c"를 행렬 연산으로 한 번에 구합니다.

Step 4 — OLS로 구하면 잔차에 제약이 생긴다
OLS는 SS_res를 각 파라미터로 미분해서 0으로 놓습니다.
∂SS_res/∂c = 0 → Σeᵢ = 0
∂SS_res/∂a = 0 → Σ(온도ᵢ × eᵢ) = 0
∂SS_res/∂b = 0 → Σ(압력ᵢ × eᵢ) = 0

파라미터 3개 → 잔차에 제약 조건 3개가 자동으로 걸립니다.

Step 5 — 잔차 예시로 제약 확인 (절편만 있는 단순 모델)
수율 = c, 데이터 4개: [80, 85, 90, 95]
OLS → c = 평균 = 87.5
잔차: e₁=-7.5, e₂=-2.5, e₃=+2.5, e₄=+7.5

제약: Σeᵢ = 0
e₁, e₂, e₃을 아무렇게나 정하면 e₄는 자동으로 결정됩니다.
e₄ = -(e₁+e₂+e₃) = -(-7.5-2.5+2.5) = 7.5
e₄는 선택의 여지가 없습니다.

파라미터가 늘수록 제약이 늘고 → 자유롭게 움직일 수 있는 잔차가 줄어듭니다.

자유도 = 독립적으로 움직일 수 있는 잔차의 수 = n - (p+1) = n-p-1
SS_res를 이 숫자로 나누는 건 "독립적인 정보 1개당 오차가 얼마인가"로 단위를 맞추는 겁니다.
100개 잔차 중 독립적인 건 97개뿐이므로 100이 아닌 97로 나눠야 오차를 제대로 추정합니다.

그런데 (n-p-1) 보정이 정확하지 않은 이유

이 보정은 "변수 1개 = 방정식 1개 소비"라고 가정합니다.
하지만 현실에서는 세 가지 상황에서 부정확해집니다.

• 변수들이 서로 상관이 높을 때(다중공선성) → 두 변수가 사실상 같은 정보인데 방정식 2개로 취급
• 변수의 노이즈 강도를 반영 못 함 → 유용한 변수 1개와 쓸모없는 변수 1개의 패널티가 동일
• n이 작을수록 → (n-p-1)이 작아져 보정 자체가 불안정해짐

그래서 실무에서는
Adjusted R²는 "변수를 추가했을 때 방향이 맞는지" 빠르게 확인하는 참고 지표로만 씁니다.
최종 판단은 Test R² 또는 Cross-Validation으로 합니다.
새 데이터에서 실제 성능이 어떻게 나오는지 직접 측정하는 게 수식 보정보다 훨씬 신뢰할 수 있습니다.

조화 평균
Accuracy 96.5%의 함정 — 불량 5개를 놓쳤다

Accuracy 96.5%만 보면 "매우 좋은 모델"처럼 보입니다.
그런데 실제 불량 20개 중 5개를 정상으로 분류(FN = 5)했습니다.

불량품이 공정을 통과해서 고객에게 출하되거나 다음 공정으로 넘어갑니다.
Accuracy는 "대부분 맞췄다"고 말하지만, 현업 관점에서는 치명적인 실패입니다.

→ 불량 감지에서 Accuracy 하나만 보는 건 위험합니다.

Precision vs Recall — 무엇을 우선해야 하는가
Precision 우선 — 오경보 비용이 클 때

"불량이라고 판정한 것 중 실제 불량 비율"

Precision이 낮으면 → 정상품을 불량으로 오판 → 라인 불필요한 정지, 양품 폐기 비용

적합한 상황: 불량 판정 시 라인 정지 비용이 매우 클 때, 고비용 재검사가 필요할 때

Recall 우선 — 불량 누출 비용이 클 때 ← 제조 불량 감지

"실제 불량 중 잡아낸 비율"

Recall이 낮으면 → 불량이 공정 통과 → 고객 클레임, 리콜, 안전 사고

대부분의 불량 감지 시나리오는 Recall이 더 중요합니다.
FN(불량을 놓치는 것)의 비용이 FP(오경보)보다 훨씬 크기 때문입니다.

F1 Score — Precision과 Recall의 균형

F1 = 2 × (Precision × Recall) / (Precision + Recall)

Precision과 Recall 중 하나가 극단적으로 낮으면 F1도 낮아집니다 (조화 평균의 특성).
불균형이 심한 데이터에서 Accuracy 대신 F1을 주 지표로 쓰는 경우가 많습니다.

단, F1도 한계가 있습니다 — Precision과 Recall의 상대적 중요도를 반영하지 않습니다.
불량 감지처럼 Recall이 훨씬 중요하면 F1보다 Recall을 직접 기준으로 삼는 게 맞습니다.

"불량 감지 모델 A: Precision 80%, Recall 60% / 모델 B: Precision 50%, Recall 90% — 어떤 모델을 선택하겠습니까? 이유는?"
04 분류 지표 ② — ROC-AUC / PR-AUC 8 min
Precision, Recall, F1은 분류 임계값(threshold)을 고정했을 때의 성능입니다. ROC-AUC와 PR-AUC는 모든 임계값에서의 성능을 종합합니다.
임계값(Threshold)이란

분류 모델은 보통 "불량 확률"을 출력합니다. 예: P(불량) = 0.73
이 확률이 임계값(예: 0.5) 이상이면 "불량"으로 판정합니다.

임계값을 낮추면(예: 0.3) → 더 많이 불량으로 판정 → Recall↑, Precision↓
임계값을 높이면(예: 0.7) → 더 적게 불량으로 판정 → Recall↓, Precision↑

ROC 곡선과 PR 곡선은 임계값을 0~1로 바꿔가며 성능이 어떻게 변하는지 보여줍니다.

왜 Recall을 높이면 Precision이 떨어지는가 — 본질
임계값을 낮춘다 = 그물을 더 넓게 친다

모델은 각 샘플에 대해 "불량일 확률"을 0~1 사이 숫자로 출력합니다.
임계값 0.5 → "확률 50% 이상이면 불량 판정"
임계값 0.3 → "확률 30% 이상이면 불량 판정"

임계값을 낮추면 더 많은 샘플이 "불량 판정"을 받습니다.
그 안에는 진짜 불량도 더 많이 포함되지만(Recall↑),
애매한 정상 샘플도 더 많이 끌려들어옵니다(FP↑ → Precision↓).

수치로 보는 트레이드오프 — 전체 1000개, 실제 불량 20개
임계값 불량 판정 수 그 중 진짜 불량 (TP) 오경보 (FP) 놓친 불량 (FN) Recall Precision
0.7 (높음) 12 10 2 10 10/20 = 50% 10/12 = 83%
0.5 (기본) 25 15 10 5 15/20 = 75% 15/25 = 60%
0.3 (낮음) 69 19 50 1 19/20 = 95% 19/69 = 28%
임계값 0.7 — "확실한 것만 불량 판정"

불량 20개 중 10개를 놓칩니다(FN=10).
하지만 불량이라 판정한 12개 중 10개는 진짜 불량입니다(Precision 83%).

문제: 놓친 불량 10개가 공정을 통과합니다.
제조 불량 감지에서 이건 허용하기 어렵습니다.

임계값 0.3 — "조금이라도 의심스러우면 불량 판정"

불량 20개 중 19개를 잡습니다(Recall 95%).
하지만 불량 판정 69개 중 50개는 사실 정상품입니다(FP=50).

결과: 오경보가 많아 라인이 자주 멈추지만,
불량 누출은 거의 없습니다. 제조 불량 감지에서는 이쪽이 대체로 낫습니다.

핵심 — Precision과 Recall은 같은 파이를 나눠 갖는다

임계값을 어떻게 설정하든 모델의 실제 판별 능력 자체는 바뀌지 않습니다.
임계값은 그 능력을 어떤 방향으로 쓸지 결정하는 것뿐입니다.

Recall을 올리려면 → 더 많이 불량 판정 → FP가 늘어남 → Precision 하락
Precision을 올리려면 → 더 적게 불량 판정 → FN이 늘어남 → Recall 하락

둘 다 100%로 만들 수 있는 유일한 방법: 모델의 판별 능력 자체를 높이는 것.
더 좋은 특성(Feature)을 쓰거나, 더 좋은 모델을 쓰는 것 — 임계값 조정으로는 불가능합니다.

→ ROC/PR 곡선이 이 "능력 자체"를 보여줍니다. 임계값이 달라져도 같은 곡선 위에 있습니다.

FPR = FP / (FP + TN)

X가 커진다 = 오경보가 늘어난다

Y축 — TPR = Recall (감지율)
TPR = TP / (TP + FN)
"실제 불량 중 잡아낸 비율"
Y가 커진다 = 불량을 더 많이 잡는다

임계값을 낮출수록 → X도↑, Y도↑ (오른쪽 위로 이동)
임계값을 높일수록 → X도↓, Y도↓ (왼쪽 아래로 이동)

이상적 모델: 왼쪽 위 꼭짓점(FPR=0, Recall=1)
오경보 없이 불량 100% 감지

랜덤 기준선 = 0.5 — 왜?
랜덤 모델은 데이터를 보지 않고 확률을 뽑습니다.
임계값을 낮추면 불량도 더 잡지만(TPR↑),
정상도 똑같은 비율로 오경보가 납니다(FPR↑).
→ TPR과 FPR이 항상 같이 움직임
→ 곡선이 대각선(y=x) 위에 찍힘
→ 대각선 아래 면적 = 0.5

단, 이는 데이터가 충분할 때의 기댓값입니다.
불량 샘플이 적으면 랜덤 모델도 AUC가 0.5에서 벗어날 수 있습니다(큰 수의 법칙).
PR Curve & PR-AUC
X축 — Recall (감지율)
"실제 불량 중 잡아낸 비율"
X가 커진다 = 불량을 더 많이 잡는다

Y축 — Precision (정밀도)
"불량이라 판정한 것 중 실제 불량 비율"
Y가 커진다 = 오경보가 줄어든다

임계값을 낮출수록 → X↑(더 잡음), Y↓(오경보 증가)
임계값을 높일수록 → X↓(더 놓침), Y↑(오경보 감소)

이상적 모델: 오른쪽 위 꼭짓점(Recall=1, Precision=1)
오경보 없이 불량 100% 감지

랜덤 기준선 = 불량 비율(2%) — 왜 0.5가 아닌가
랜덤 모델은 Recall과 무관하게
Precision = 불량 비율에 수렴합니다.
불량 판정을 아무리 많이 내려도,
그 안에서 진짜 불량 비율은 2%뿐이기 때문입니다.
→ 곡선이 y=0.02 수평선에 붙어버림

ROC와 달리 PR-AUC 랜덤 기준선은
데이터마다 다릅니다 (= 불량 비율).
ROC-AUC의 착시 — 불균형 데이터에서 왜 과대평가되는가

핵심은 FPR 분모에 TN이 들어간다는 겁니다.

FPR = FP / (FP + TN)
TPR = TP / (TP + FN)

정상 9980개, 불량 20개인 데이터에서 오경보(FP)가 100개 나도:
FPR = 100 / (100 + 9880) = 1%

TN이 크면 FPR이 작게 유지됩니다. X축이 거의 움직이지 않습니다.
곡선이 왼쪽에 붙어 있어서 AUC가 높아 보입니다.

TPR은 분모가 실제 불량 수(20개)라 TN 크기와 무관합니다.
결국 TN이 크면 FPR만 낮게 유지되고 → X축이 잘 안 움직이고 → AUC가 실제보다 높게 나옵니다.

불량을 전혀 못 잡는 나쁜 모델도 TN이 크면 ROC-AUC가 높게 나올 수 있습니다.

PR-AUC가 더 엄격한 이유:
Precision = TP / (TP + FP)
Recall   = TP / (TP + FN)

Precision 분모는 TP + FP입니다. TN이 분모에 직접 들어가지 않습니다.
Recall 분모도 TP + FN입니다. 마찬가지로 TN과 무관합니다.

Negative가 아무리 많아도 TN이 PR 곡선 계산에 직접 개입하지 않습니다.
모델이 FP를 얼마나 내는지, FN을 얼마나 내는지만 반영됩니다.

ROC-AUC와의 구조적 차이가 바로 이겁니다.
FPR = FP / (FP + TN) — TN이 분모에 직접 들어갑니다.
Negative가 많으면 모델 성능과 무관하게 FPR이 자동으로 작아집니다.
모델이 아무리 FP를 많이 내도, TN이 크면 FPR이 작게 유지되어 X축이 안 움직입니다.

요약: ROC-AUC는 TN이 지표 계산에 직접 개입해서 Negative가 많을수록 구조적으로 과대평가됩니다.
PR-AUC는 TN이 계산에 개입하지 않아 그 편향이 없습니다.

달성 가능 여부 판단은 두 단계로 나뉩니다.
Stage 1 — 애초에 AI 모델로 해결 가능한 문제인가 (모델 개발 전)
Stage 2 — 요구하는 지표 수준이 현실적인가 (모델 개발 후)
Stage 1 — AI 모델 개발이 가능한 상황인가 (모델 개발 전)
이 단계는 성과지표의 영역이 아닙니다

"Recall 95% 달성 가능한가?"를 묻기 전에, 더 근본적인 질문이 있습니다.
"불량과 정상이 데이터로 구분 가능한 문제인가?"

아무리 좋은 모델을 써도, 불량과 정상의 특성값 분포가 완전히 겹쳐 있으면 어떤 지표 목표도 달성할 수 없습니다.
이 판단은 모델을 만들기 전, 데이터를 탐색하는 단계에서 해야 합니다.

모델 개발 전 확인 방법:
• 핵심 특성 1~2개를 골라 불량/정상 샘플 분포를 같은 축에 시각화 — 겹치는 정도를 직접 봅니다
• 특성 하나씩 불량/정상의 평균과 분산을 비교 — 평균 차이가 크고 분산이 작으면 구분 가능성이 높습니다
• 도메인 전문가에게 물어봅니다 — "이 센서값만 보고 사람이 불량인지 판단할 수 있는가?"
사람도 구분 못 하는 데이터라면 모델도 구분하기 어렵습니다.

이 탐색 과정(EDA)은 추후 별도 세션에서 다룹니다.
지금 단계에서는 "모델 개발 전 이 검토가 반드시 선행돼야 한다"는 것만 기억하면 됩니다.

Stage 2 — 요구하는 지표 수준이 현실적인가 (모델 개발 후)
Stage 1을 통과해서 모델을 만들었습니다.
이제 "Recall 95% 달성해주세요"라는 요구에 근거 있게 답할 수 있어야 합니다.
PR 곡선으로 목표 달성 가능 여부를 읽는 방법

PR 곡선은 임계값을 바꿔가며 Recall과 Precision이 어떻게 변하는지 보여줍니다.
Recall을 높이면 Precision이 얼마나 빠르게 떨어지는지가 곡선의 모양에 나타납니다.

곡선이 완만하게 내려온다 → Recall을 올려도 Precision이 크게 안 떨어짐 → 목표 달성 가능성 높음
곡선이 급격히 내려온다 → Recall을 조금만 올려도 Precision이 급락 → 불량/정상 구분이 어려운 상황

PR 곡선에서 목표 Recall 지점을 찍었을 때 Precision이 얼마인지 읽으면 됩니다.
Precision이 너무 낮으면 → 기술적으로 가능해도 운영 불가능.
이 판단을 현업과 함께 해야 합니다 — "이 수준에서 오경보가 N배 늘어납니다. 감수하시겠습니까?"
불량 샘플이 충분한가 — 샘플 수도 상한을 결정한다

불량 샘플이 20개밖에 없는데 Recall 95%를 요구하면, 모델이 그 20개의 패턴을 일반화하기 어렵습니다.

• 불량 샘플 100개 미만 → 높은 Recall 목표는 불안정. 데이터 추가 수집이 선행돼야 합니다
• SMOTE 등 오버샘플링은 보완책이지 근본 해결책이 아닙니다

현업에게 말해야 할 것: "불량 샘플이 N개입니다. 목표 수준을 달성하려면 최소 M개가 필요합니다."

현업 요구에 대응하는 3단계 답변 구조
Step 1 — 현재 모델의 PR 곡선을 먼저 보여준다

"현재 모델에서 Recall을 90%로 설정하면 Precision은 X%입니다."
숫자를 먼저 제시해야 논의가 시작됩니다. 가능/불가능 판단 전에 현황을 공유합니다.

Step 2 — 목표 달성을 막는 제약 조건을 명시한다

"현재 불량 샘플이 N개라 Recall 95%에서 Precision이 X% 이하로 떨어집니다."
"불량/정상 특성값 분포가 겹치는 구간이 있어 이 이상은 데이터 수준의 한계입니다."
— 모델의 문제가 아니라 데이터 또는 문제 자체의 구조적 한계임을 명확히 합니다.

Step 3 — 달성 가능한 조건 또는 대안을 제시한다

"불량 샘플을 N개 이상 추가 수집하면 목표 수준에 근접할 수 있습니다."
"Recall 95% 대신 90%로 낮추면 Precision을 X%로 유지할 수 있습니다."
"2단계 검사(1차 모델 → 의심 샘플만 2차 정밀 검사) 구조로 목표를 충족할 수 있습니다."
— "안 된다"로 끝내는 게 아니라 무엇이 바뀌면 가능한지를 함께 제시합니다.

토론 질문 4
"현업 담당자가 'Recall 95% 이상은 돼야 현장에 쓸 수 있다'고 합니다. 현재 모델은 Recall 78%, PR-AUC 0.41입니다. 어떻게 대응하겠습니까?"
05 지표의 한계 & 현업 기준과의 비교 10 min
지표가 좋아도 모델이 틀리는 3가지 경우
  • ✕
    ① 구간 편향 — 중요한 구간에서만 체계적으로 틀린다
    전체 R² 0.93이지만 수율 70% 이하 구간(위험 영역)에서만 RMSE가 3배 높을 수 있습니다. 전체 평균 지표는 정상 구간이 대부분이어서 위험 구간의 오차를 희석합니다. → 구간별 RMSE, 구간별 Recall을 따로 측정해야 합니다
  • ✕
    ② 공정 변화 — 지표는 학습 데이터 기준
    R² 0.91은 "학습 데이터와 비슷한 조건"에서의 성능입니다. 설비 교체, 원자재 변경, 계절 변화 후에는 같은 모델이 전혀 다른 성능을 냅니다. → 정기적으로 성능 재측정 필요. 지표가 갑자기 떨어지면 공정 변화 신호로 읽어야 합니다
  • ✕
    ③ 데이터 누수 — 지표가 좋으면 오히려 의심해야 한다
    불량 발생 후에만 측정되는 변수가 특성으로 들어가 있으면, 모델이 "정답을 미리 아는 것"처럼 학습됩니다. AUC 0.99, Recall 98%가 나와도 실제로는 쓸 수 없는 모델. Train R²이 0.99인데 Test R²이 0.72이면 누수 또는 과적합을 강하게 의심해야 합니다
현업 기준과의 비교 — Cpk / Ppk vs ML 지표
공정 능력 지표 — Cpk / Ppk

질문: "공정이 스펙 범위 안에 드는가?"

Cpk = min(USL-μ, μ-LSL) / (3σ)
→ 공정 중심이 스펙 중앙에서 얼마나 벗어났는지 포함

Cpk ≥ 1.33 → 일반적으로 양호
Cpk < 1.0 → 스펙 이탈 발생 가능

Ppk는 단기 변동(σ_within) 대신 전체 변동(σ_overall) 사용 → 더 보수적

ML 성과 지표 — RMSE / Recall

질문: "모델이 실제값을 얼마나 잘 예측하는가?"

RMSE = 예측값과 실제값의 평균 오차 크기
Recall = 불량을 얼마나 빠짐없이 잡는가

"모델 성능이 좋다" ≠ "공정이 안정적이다"
"공정 Cpk가 높다" ≠ "ML 모델이 필요 없다"

두 기준은 다른 질문에 답하는 것

ML 지표가 좋아도 Cpk/Ppk가 안 좋을 수 있다 — 왜?

ML 모델이 y를 잘 맞췄다고 해서 Cpk/Ppk가 자동으로 좋아지지 않습니다.

이유는 간단합니다. ML 모델이 맞추는 y가 Cpk/Ppk와 연결되지 않는 y일 수 있기 때문입니다.

예를 들어 모델이 "수율 예측 RMSE 1.2%"를 달성했어도 — 그 수율이 스펙 한계(USL/LSL)와 어떤 관계인지는 별개의 문제입니다.
모델이 평균 구간에서는 잘 맞추지만, 스펙 이탈이 발생하는 극단 구간에서 체계적으로 틀린다면 Cpk는 여전히 낮습니다.

해결책 — y를 현장 지표와 연결되도록 설정해야 한다

ML 지표(RMSE, Recall)와 현장 지표(Cpk, Ppk)가 함께 좋아지려면,
애초에 y를 잘 설정하는 것이 핵심입니다.

잘못된 y 설정: "수율 평균값 예측"
→ RMSE가 낮아도 스펙 이탈 여부와 무관 → Cpk 개선 안 됨

올바른 y 설정: "스펙 이탈 여부 예측" 또는 "스펙 대비 편차 예측"
→ 모델이 잘 맞출수록 스펙 이탈이 줄어듦 → Cpk/Ppk 개선과 직결

즉 y를 설정할 때 "이 y를 잘 맞추면 현장에서 어떤 변화가 생기는가?"를 먼저 생각해야 합니다.
ML 지표가 좋은 모델을 만드는 것보다, 현장 지표와 연결되는 y를 정의하는 것이 더 앞선 문제입니다.

현업에게 지표를 설명할 때 번역이 필요한 이유

"RMSE 1.8%입니다" → 현업: "그게 좋은 건가요?"
"Cpk 기준으로 ±3σ = ±2.4%이고, 모델 오차가 그 범위 안에 있습니다" → 이해 가능

"Recall 85%입니다" → 현업: "그게 무슨 뜻이죠?"
"불량 100개 중 85개는 잡고, 15개는 통과시킵니다" → 이해 가능

지표 숫자보다 그 숫자가 현업 비용 구조에서 어떤 의미인지 연결하는 것이 핵심입니다.

06 해석 연습 — 숫자만 보고 판단하는 함정 5 min
아래 시나리오 각각에 대해 "이 모델 써도 됩니까?"를 판단해보세요
시나리오 A — 수율 예측 회귀 모델
Train R² = 0.97 / Test R² = 0.71 / MAE = 1.9% / RMSE = 5.1%
MAE(1.9%)와 RMSE(5.1%) 격차가 큽니다 — 간헐적으로 매우 큰 오차가 발생합니다. Train/Test R² 차이(0.26)도 큽니다 — 과적합 또는 누수를 강하게 의심해야 합니다. 지표 자체보다 이 차이의 원인을 먼저 파악해야 합니다.
사용 보류 — Train/Test 차이 원인 확인 필요
시나리오 B — 불량 감지 분류 모델
Accuracy = 98.2% / Precision = 72% / Recall = 51% / ROC-AUC = 0.94 / PR-AUC = 0.43
Recall 51% — 실제 불량의 절반가량을 놓칩니다. ROC-AUC(0.94)는 좋아 보이지만 불균형 데이터에서 과대평가된 지표입니다. PR-AUC(0.43)가 실제 성능. 불량 누출 비용이 크다면 이 모델은 현장에 적용하기 어렵습니다.
사용 불가 — Recall이 허용 기준 미달
시나리오 C — 불량 감지 분류 모델 (개선 후)
Accuracy = 95.1% / Precision = 48% / Recall = 92% / PR-AUC = 0.71
Accuracy가 B보다 낮아졌지만 Recall이 92%로 올라갔습니다. 불량의 92%를 잡습니다. Precision(48%)이 낮아 오경보가 늘었지만 — 불량 누출 비용과 오경보 비용 중 어느 쪽이 더 큰지에 따라 판단이 달라집니다. 대부분의 불량 감지 상황에서는 C가 B보다 훨씬 낫습니다.
조건부 사용 가능 — 오경보 비용 감수 여부 현업 확인
이번 주 전체를 관통하는 메시지

→ "Train과 Test 성능 차이는 얼마인가?"

07 사전질문 Q&A
Q1. 지표 해석 순서 — AUROC → PR-AUC → Recall → Train/Test 차이 순서가 실무에서 유효한가?

순차적으로 보는 것도 좋지만, 복합적으로 함께 고려하는 게 더 맞습니다.

AUROC와 PR-AUC는 둘 다 임계값을 0부터 1까지 바꿔가면서 X축과 Y축이 어떻게 변하는지를 보는 지표입니다. 결국 모델의 전반적인 판별 능력을 보는 거라 두 지표를 함께 본 뒤, 임계값을 고정해서 Recall/Precision을 확인하는 흐름이 자연스럽습니다.

과적합/누수 여부는 마지막에 보되, 구체적인 기준을 갖는 게 중요합니다.
Train/Test AUC 차이가 0.1 이상이면 과적합이나 누수를 의심하는 것이 실무에서 쓸 수 있는 기준입니다. "설명이 안 될 만큼 성능이 좋다"는 주관적 판단보다 이 숫자 차이를 먼저 봐야 합니다.

Q2. 데이터를 추가해도 성능이 안 올라갈 때 — 데이터 문제인지, 모델 문제인지 어떻게 구분하는가?

우선 "X와 y가 어떤 연관이 있는가"를 먼저 봐야 합니다.

데이터를 추가하기 전에, 기존 모델이 어떤 데이터를 못 맞추는지를 먼저 분석합니다. 회귀는 극단값(extreme)을 못 맞추는 경향, 분류는 소수 범주를 못 맞추는 경향이 있습니다. 어떤 공정 조건에서 집중적으로 틀리는지, 특정 시간대나 설비에서 편향이 있는지를 보면 어떤 데이터가 부족한지가 보입니다.

y를 잘 설명하는 X를 가진 데이터를 추가하는 게 가장 좋습니다. 다만 제조 현장에서는 불량이 발생해야 불량 데이터가 생기기 때문에, 능동적으로 선택하기 어려운 경우가 많습니다. 이때는 기존 특성 중 y와 관계가 있는 변수를 발굴하는 방향을 먼저 시도합니다. 도메인 전문가와 함께 "이 불량이 발생하기 전에 어떤 공정 조건이 달랐는가"를 찾는 게 실질적인 첫 단계입니다.

모델 문제인지를 보려면, 모델 자체의 구조적 한계 때문인지 아니면 HPO 같은 조정 가능한 요소 때문인지를 먼저 구분해야 합니다. 모델 고유의 구조적 한계라면 HPO로는 해결이 안 되기 때문에, 데이터 구조를 바꾸거나 모델 자체를 교체해야 합니다.

Q3. PR 곡선 기준 최적 임계값을 찾았는데 Precision이 너무 낮아 운영 불가능하다면?

임계값을 결정할 때는 라이브러리에서 바로 predict를 쓰는 게 아니라, predict_proba 같은 메소드로 확률을 뽑아서 직접 임계값을 조정해야 합니다.

그런데 임계값 조정보다 우선순위는 모델 자체의 판별 능력입니다. 정상은 불량일 확률이 0에 가깝고, 불량은 불량일 확률이 1에 가깝도록 출력하는 능력을 높이는 것이 먼저입니다.

그 능력을 높였음에도 Precision이 너무 낮아 운영이 불가능하다면 — 이건 모델이 FP를 너무 많이 만들어낸다는 뜻입니다. 데이터 관점의 대응 방향은 두 가지입니다.

첫째, FP가 많이 발생하는 구간을 분석합니다. 어떤 정상 샘플이 불량으로 오판되는지를 보면, 불량과 경계가 모호한 정상 케이스들이 있을 겁니다. 이 케이스들의 레이블을 재검토하거나, 이 구간을 더 잘 구분할 수 있는 특성을 추가로 수집합니다.

둘째, 2단계 구조를 고려합니다. 1차 모델은 Recall 우선으로 넓게 잡고, 1차에서 불량 판정된 것만 2차 모델에서 정밀 검사하는 방식입니다. Precision과 Recall을 단일 모델로 동시에 만족하기 어려울 때 현장에서 실제로 쓰는 구조입니다.

Q4. ROC-AUC 0.99 같은 높은 성능이 나오면 반드시 누수인가? 누수 예방과 실무 패턴은?

ROC-AUC 0.99가 반드시 누수는 아닙니다. 학습 데이터와 테스트 데이터의 분포 차이가 크지 않으면 충분히 발생할 수 있습니다.

가장 명확한 기준은 Train/Test 성능 차이입니다. Train AUC 0.99, Test AUC 0.97이면 문제없습니다. Train AUC 0.99, Test AUC 0.71이면 누수 또는 과적합을 강하게 의심해야 합니다.

누수를 예방하려면 각 특성이 무엇을 의미하는지를 봐야 합니다. 핵심은 그 특성이 타겟값이 산출되기 전에 반드시 수집 가능한 값인가입니다. 추론 시점에 알 수 없는 정보가 학습에 포함된 것이 누수의 본질입니다.

실무에서 자주 발생하는 누수 패턴을 추가하면 — 타겟값 산출 이후에만 생성되는 변수 외에, 전처리 과정에서 전체 데이터의 통계값(평균, 표준편차)을 계산할 때 Test 데이터 정보가 섞이는 경우(Data Leakage in preprocessing), 그리고 시계열 데이터에서 미래 시점 데이터가 학습에 포함되는 경우가 대표적입니다.

Q5. 구간별 RMSE가 높을 때 해당 구간 데이터에 가중치를 주는 방식이 맞는가?

그 방식은 적절하지 않습니다. 해당 데이터를 틀렸을 때 더 많은 가중치를 주면, 반대로 그 구간에 편향적으로 학습되어 오히려 다른 구간에서 성능이 나빠질 수 있습니다. 어떤 모델을 쓰는지에 따라서도 달라집니다.

올바른 접근은 먼저 왜 그 구간에서 틀리는지 원인을 찾는 것이 선행돼야 합니다.

• 해당 구간의 학습 데이터 샘플이 충분한지 확인합니다. 샘플이 부족한 거라면 해당 구간 데이터를 추가 수집하는 게 맞습니다.
• 그 구간에서만 나타나는 특성 패턴이 있는지 봅니다. 그 구간을 잘 설명하는 변수가 빠져 있다면, 관련 특성을 새로 발굴해야 합니다.
• 데이터나 특성 문제가 아닌 경우에 한해서, 그때 모델 구조 변경이나 구간별 별도 모델을 고려합니다.
