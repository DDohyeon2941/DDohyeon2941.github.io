Week 3 session summary

Clustering does not provide the answer. It only divides the data.
People, rather than the algorithm, must decide whether those divisions are meaningful.

How to report clustering results appropriately:
❌ "Cluster 1 is the high-risk cluster."
✅ "We found a pattern of higher defect rates under high-temperature, high-pressure, low-flow conditions. These conditions could serve as monitoring criteria."

Causation ≠ correlation

Clustering found the pattern "more defects occurred under these conditions," rather than the cause "these conditions create defects." The same applies to this week's metrics: good numbers do not necessarily mean a model is correct.

Domain validation is essential

Always check whether you can give the results a meaningful name and whether they make sense in practice. Even excellent metrics cannot be trusted if they conflict with the operational context.

01 How to read metrics — The trap of an "average report card" 5 min
Key question: Performing well "overall" differs from performing well "in important regions." Which does the metric show?
A metric = an aggregate summary of the full dataset

RMSE 1.2, accuracy 97%, AUC 0.93 — These numbers all summarize performance across the full dataset.

In manufacturing, however, the "overall average" is often not what matters most.

At a defect rate of 0.5%, missing all 50 defective cases still gives accuracy of 99.5% if the 9950 normal cases are correct.
In yield prediction, a model can fit the normal range (85–95%) well and systematically miss the high-risk range (60% or below), yet still achieve R² 0.92.

Why one metric is insufficient for a conclusion

Good metrics can hide problems:
• Systematically missing important minority cases (defects)
• Errors concentrated in specific operating-condition ranges
• An illusion created by training-data leakage
• Application to data from changed operating conditions

How to use metrics properly

Use metrics as a starting point, then:
• Inspect residuals to locate large errors
• Evaluate defective cases separately
• Check the train–test performance gap
• Compare with operational criteria (Cpk, specification limits)

02 Regression metrics — MAE / RMSE / R² / Adjusted R² 15 min
Shared scenario: A model predicting process yield (%). y = actual yield; ŷ = predicted yield. Normal range: 85–95%; high-risk range: 70% or below.
MAE
Mean Absolute Error — MAE
The mean absolute error. It has the same units as y and is less sensitive to outliers.
Formula
MAE = (1/n) × Σ|y - ŷ|
Intuitively shows how far predictions deviate on average.
Yield prediction MAE = 2.1% → "The average error is ±2.1%."
Manufacturing interpretation
Advantages: Business stakeholders can readily understand the error magnitude.
"An MAE of 2% means yield predictions are off by 2% on average." — Intuitive

Limitations: Treats large and small errors with the same weighting
Treats the error from predicting 92% for an actual yield of 90% (2%)
the same as predicting 62% for an actual yield of 60% (2%).
✓ Suitable when
Outliers are common or extreme values are less important; when explaining error magnitude to business stakeholders.
! Caution
Also inspect RMSE when large errors are critical, such as defect detection or prediction in high-risk ranges.
RMSE
Root Mean Squared Error — RMSE
The square root of the mean squared error. More sensitive to large errors; it has the same units as y.
Formula
RMSE = √((1/n) × Σ(y - ŷ)²)
Squaring errors means that a single large error can sharply increase RMSE.
Always greater than or equal to MAE (RMSE ≥ MAE).
MAE vs RMSE — The difference
For errors [1, 1, 1, 1, 10]:
→ MAE = (1+1+1+1+10)/5 = 2.8
→ RMSE = √((1+1+1+1+100)/5) = 4.6

The single large error (10) substantially increases RMSE.
RMSE ≫ MAE → large errors occur intermittently is the implication.
✓ Suitable when
When large errors are critical and require a penalty, such as prediction in high-risk ranges or equipment anomaly detection.
✕ Caution
If outliers are contaminated data, they can dominate RMSE. Check data quality first.
R²
R-squared — Coefficient of determination
How much of the variance in y the model explains. 0–1 (negative values are also possible). Dimensionless.
Formula
R² = 1 - SS_res / SS_tot

SS_res = Σ(y - ŷ)² ← Model error
SS_tot = Σ(y - ȳ)² ← Total variation
R² = 1.0 → Perfect prediction
R² = 0.0 → Equivalent to predicting only the mean
R² < 0.0 → Worse than predicting the mean (possible!)
Three R² pitfalls
① R² increases as variables are added
Even irrelevant variables cannot reduce R².
→ See the explanation below.

② It can be negative
R² can be negative on data outside the training range.

③ It hides bias across ranges
A model can fit the normal range and fail in the high-risk range,
yet achieve an overall R² of 0.95.
! Always check when R² is 0.9x
What does the residual plot show for errors in the high-risk yield range (70% or below)? Computing RMSE for that range alone may reveal a very different picture.
✕ Caution
Do not compare models with different numbers of variables using R² alone → Adjusted R² is needed.
Why adding variables increases R² — The underlying reason

Adding a variable gives the model two options.

If the variable is useful → Use it to reduce errors → R² increases.
If the variable is irrelevant → Give it a coefficient close to 0 and effectively ignore it → R² stays the same.

Neither case lowers R². At worst, it remains unchanged.
Adding a variable gives the model "an opportunity to do better," rather than "an obligation to do better."

The problem is "patterns found by chance."
Adding 25 variables unrelated to yield (e.g., the last digits of an employee ID or a measurement sequence number)
allows the model to learn chance patterns found only in the training data.
→ Training R² = 0.91 (higher)
→ New-data R² = 0.74 (lower instead)

Concluding "more variables are better" from R² alone leads to overfitting.
Always check test R² and adjusted R² together when adding variables.

Adj R²
Adjusted R² — Adjusted coefficient of determination
R² with a penalty for the number of variables, allowing fairer model comparison.
Formula — How the adjustment works
Adj R² = 1 - SS_res / (n-p-1)
────────────────
SS_tot / (n-1)

n = number of samples / p = number of variables
There is one difference from R².
Divide SS_res by (n-p-1).

As the number of variables (p) increases → (n-p-1) decreases.
→ SS_res/(n-p-1) increases.
→ Adjusted R² decreases.

If the benefit of adding a variable (a decrease in SS_res)
is smaller than the penalty (a decrease in n-p-1),
adjusted R² decreases.
Numerical example
Model A: 5 variables, R² = 0.88, adjusted R² = 0.87
Model B: 30 variables, R² = 0.91, adjusted R² = 0.84

R² alone makes B look better.
Adjusted R² favors A.

B added 25 variables to raise R² by 0.03,
but the penalty exceeded the actual increase in explanatory power.

A decrease in adjusted R² = The newly added variable
did not materially help the model.
✓ Use cases
Compare models with different numbers of variables. Use as a reference when selecting variables from manufacturing data with many sensors.
✕ Limitation — The penalty is not exact
The (n-p-1) adjustment is based on degrees of freedom. "One variable = exactly this penalty" does not always match reality. It becomes unstable when variables are highly correlated or n is small. → Measuring performance directly with a train–test split or cross-validation is more reliable.
Where (n-p-1) comes from — Equations, OLS, and degrees of freedom

Step 1 — What is an equation?
"An equality containing unknown values."
To identify unknowns, we need as many equations as unknowns.

Step 2 — One data point = one equation
A model with two variables: Yield = a×Temperature + b×Pressure + c
Unknowns a, b, c — Three in total

Insert one data point (temperature=85, pressure=3.2, yield=91):
91 = a×85 + b×3.2 + c
The numbers are fixed; only a, b, c are unknown → One equation
Each additional data point adds another equation.

Step 3 — The relationship between equations and unknowns
Equations < unknowns → Infinitely many solutions (the model is underdetermined)
Equations = unknowns → One solution → SS_res = 0 → The data have been memorized
Equations > unknowns → No perfect solution → Residuals arise → Error can actually be measured

In regression, we want the third case.
100 data points and 3 unknowns → No solution satisfies all 100 equations simultaneously.
→ OLS finds "the a, b, c that minimize the sum of squared residuals" in one matrix calculation.

Step 4 — Solving with OLS constrains the residuals
OLS differentiates SS_res with respect to each parameter and sets the derivatives to 0.
∂SS_res/∂c = 0 → Σeᵢ = 0
∂SS_res/∂a = 0 → Σ(Temperatureᵢ × eᵢ) = 0
∂SS_res/∂b = 0 → Σ(Pressureᵢ × eᵢ) = 0

Three parameters automatically impose three constraints on the residuals.

Step 5 — Checking constraints with residuals (an intercept-only model)
Yield = c, with four data points: [80, 85, 90, 95]
OLS → c = mean = 87.5
Residuals: e₁=-7.5, e₂=-2.5, e₃=+2.5, e₄=+7.5

Constraint: Σeᵢ = 0
Once e₁, e₂, and e₃ are chosen, e₄ is determined automatically.
e₄ = -(e₁+e₂+e₃) = -(-7.5-2.5+2.5) = 7.5
e₄ has no freedom of choice.

More parameters mean more constraints → Fewer residuals can vary independently.

Degrees of freedom = number of independently varying residuals = n - (p+1) = n-p-1
Dividing SS_res by this number expresses the error "per independent piece of information."
Only 97 of 100 residuals are independent, so divide by 97 rather than 100 to estimate the error properly.

Why the (n-p-1) adjustment is not exact

The adjustment assumes "one variable consumes one equation."
In practice, it becomes inaccurate in three situations.

• Highly correlated variables (multicollinearity) → Two variables contain essentially the same information but count as two equations.
• Variable noise is not reflected → A useful variable and an irrelevant variable receive the same penalty.
• Small n → (n-p-1) becomes small and the adjustment itself becomes unstable.

In practice, therefore,
adjusted R² serves only as a quick reference for whether adding a variable is helping.
Make the final judgment using test R² or cross-validation.
Directly measuring performance on new data is much more reliable than a formula-based correction.

The trap of 96.5% accuracy — Five defects were missed

Accuracy of 96.5% alone suggests "a very good model."
However, of the 20 actual defects, 5 were classified as normal (FN = 5).

Defective items pass through the process and are shipped to customers or sent to the next process.
Accuracy says "most predictions were correct," but operationally this is a critical failure.

→ It is dangerous to look only at accuracy for defect detection.

Precision vs recall — Which takes priority?
Prioritize precision — When false alarms are costly

"The proportion of predicted defects that are actually defective"

Low precision → Good items misclassified as defective → Unnecessary line stoppages and scrapping costs

Suitable situations: When stopping the line after a defect flag is very costly or expensive reinspection is required

Prioritize recall — When escaped defects are costly ← Manufacturing defect detection

"The proportion of actual defects detected"

Low recall → Defects pass through the process → Customer complaints, recalls, safety incidents

Recall matters more in most defect detection scenarios.
The cost of FN (missing a defect) is much higher than the cost of FP (a false alarm).

F1 score — Balancing precision and recall

F1 = 2 × (Precision × Recall) / (Precision + Recall)

If either precision or recall is extremely low, F1 is also low (a property of the harmonic mean).
F1 is often used instead of accuracy as the main metric for severely imbalanced data.

However, F1 also has a limitation: it does not reflect the relative importance of precision and recall.
When recall is much more important, as in defect detection, use recall directly rather than F1 as the criterion.

04 Classification metrics ② — ROC-AUC / PR-AUC 8 min
Precision, recall, and F1 describe performance at a fixed classification threshold. ROC-AUC and PR-AUC aggregate performance across all thresholds.
What is a threshold?

Classification models typically output a "probability of a defect." Example: P(defect) = 0.73
If this probability meets or exceeds a threshold (e.g., 0.5), the item is classified as defective.

Lower threshold (e.g., 0.3) → More defect predictions → Recall↑, precision↓
Higher threshold (e.g., 0.7) → Fewer defect predictions → Recall↓, precision↑

ROC and PR curves show how performance changes as the threshold varies from 0 to 1.

Why increasing recall lowers precision — The underlying reason
Lowering the threshold = casting a wider net

The model outputs a number between 0 and 1 for each sample's "probability of being defective."
Threshold 0.5 → "Flag a defect at 50% probability or above."
Threshold 0.3 → "Flag a defect at 30% probability or above."

Lowering the threshold flags more samples as defective.
This includes more actual defects (recall↑),
but also draws in more ambiguous normal samples (FP↑ → precision↓).

The numerical trade-off — 1000 items, 20 actual defects
Threshold Predicted defects Actual defects among them (TP) False alarms (FP) Missed defects (FN) Recall Precision
0.7 (high) 12 10 2 10 10/20 = 50% 10/12 = 83%
0.5 (default) 25 15 10 5 15/20 = 75% 15/25 = 60%
0.3 (low) 69 19 50 1 19/20 = 95% 19/69 = 28%
Threshold 0.7 — "Flag only clear defects."

10 of the 20 defects are missed (FN=10).
However, 10 of the 12 flagged items are actual defects (precision 83%).

Problem: 10 missed defects pass through the process.
This is difficult to accept in manufacturing defect detection.

Threshold 0.3 — "Flag anything even slightly suspicious."

19 of the 20 defects are detected (recall 95%).
However, 50 of the 69 flagged items are actually normal (FP=50).

Result: Frequent false alarms cause repeated line stoppages,
but almost no defects escape. This is generally preferable in manufacturing defect detection.

Key point — Precision and recall share the same pie

Whatever threshold is chosen, the model's underlying ability to discriminate does not change.
The threshold only determines how that ability is used.

Increase recall → Flag more defects → FP increases → Precision falls
Increase precision → Flag fewer defects → FN increases → Recall falls

The only way to make both 100%: Improve the model's underlying ability to discriminate.
Use better features or a better model: threshold adjustment cannot achieve this.

→ ROC/PR curves show this "underlying ability." Different thresholds remain on the same curve.

ROC Curve & AUC
X-axis — FPR (false positive rate)
FPR = FP / (FP + TN)
"The proportion of normal samples incorrectly flagged as defective"
Larger X = more false alarms

Y-axis — TPR = recall (detection rate)
TPR = TP / (TP + FN)
"The proportion of actual defects detected"
Larger Y = more defects detected

Lower threshold → X↑ and Y↑ (move toward the upper right)
Higher threshold → X↓ and Y↓ (move toward the lower left)

Ideal model: Upper-left corner (FPR=0, recall=1)
Detect 100% of defects with no false alarms

Random baseline = 0.5 — Why?
A random model generates probabilities without looking at the data.
Lowering the threshold detects more defects (TPR↑),
but produces false alarms on normal cases at the same rate (FPR↑).
→ TPR and FPR always move together.
→ The curve lies on the diagonal (y=x).
→ The area below the diagonal = 0.5.

This is the expected value when sufficient data are available.
With few defect samples, even a random model's AUC can differ from 0.5 (the law of large numbers).
PR Curve & PR-AUC
X-axis — Recall (detection rate)
"The proportion of actual defects detected"
Larger X = more defects detected

Y-axis — Precision
"The proportion of predicted defects that are actually defective"
Larger Y = fewer false alarms

Lower threshold → X↑ (detect more), Y↓ (more false alarms)
Higher threshold → X↓ (miss more), Y↑ (fewer false alarms)

Ideal model: Upper-right corner (recall=1, precision=1)
Detect 100% of defects with no false alarms

Random baseline = defect prevalence (2%) — Why not 0.5?
Regardless of recall, a random model's
precision approaches defect prevalence.
No matter how many samples are flagged,
only 2% of them are actual defects.
→ The curve approaches the horizontal line y=0.02.

Unlike ROC, the random PR-AUC baseline
varies by dataset (= defect prevalence).
The ROC-AUC illusion — Why it looks inflated on imbalanced data

The key is that TN appears in the denominator of FPR.

FPR = FP / (FP + TN)
TPR = TP / (TP + FN)

With 9980 normal and 20 defective items, even 100 false alarms (FP) give:
FPR = 100 / (100 + 9880) = 1%

Large TN keeps FPR small. The X-axis barely moves.
The curve stays near the left edge, making AUC appear high.

TPR's denominator is the actual number of defects (20), so it does not depend on TN.
Consequently, large TN keeps only FPR low→ The X-axis moves little → AUC appears higher than the practical performance suggests.

Even a poor model that detects no defects can show high ROC-AUC when TN is large.

Why PR-AUC is stricter:
Precision = TP / (TP + FP)
Recall   = TP / (TP + FN)

Precision's denominator is TP + FP. TN does not enter it directly.
Recall's denominator is TP + FN, also independent of TN.

However many negatives there are, TN does not directly enter the PR curve calculation.
The calculation reflects how many FP and FN the model produces.

This is the structural difference from ROC-AUC.
FPR = FP / (FP + TN) — TN enters the denominator directly.
More negatives automatically make FPR smaller, regardless of model performance.
Even when the model produces many FP, large TN keeps FPR small and limits movement along the X-axis.

Summary: ROC-AUC uses TN directly in its calculation, making it structurally overoptimistic as the number of negatives increases.
PR-AUC does not use TN directly and avoids that bias.

04+ When business stakeholders request a target metric — Assessing feasibility 10 min
Feasibility assessment has two stages.
Stage 1 — Can an AI model solve this problem at all? (Before model development)
Stage 2 — Is the requested metric level realistic? (After model development)
Stage 1 — Is AI model development feasible? (Before model development)
This stage is outside the scope of performance metrics.

Before asking "Can we achieve 95% recall?", ask a more fundamental question.
"Can the data distinguish defective from normal cases?"

Even the best model cannot meet a metric target if the feature distributions of defective and normal cases overlap completely.
Make this assessment during data exploration, before building the model.

Checks before model development:
• Select 1–2 key features and plot defective/normal distributions on the same axes to inspect their overlap directly.
• Compare defective/normal means and variances for each feature. Large mean differences and small variances suggest better separability.
• Ask a domain expert: "Could a person identify a defect from these sensor readings alone?"
If people cannot distinguish the cases from the data, a model will also struggle.

This exploratory process (EDA) will be covered in a separate session.
For now, remember that "this review must precede model development".

Stage 2 — Is the requested metric level realistic? (After model development)
The problem passed Stage 1, and a model has been built.
Now you need an evidence-based response to "Please achieve 95% recall."
Reading target feasibility from a PR curve

A PR curve shows how recall and precision change across thresholds.
The curve's shape shows how quickly precision falls as recall increases.

The curve declines gradually → Precision falls little as recall rises → The target is more likely feasible.
The curve declines sharply → A small recall increase causes a sharp precision drop → Defects and normal cases are difficult to separate.

Locate the target recall on the PR curve and read the corresponding precision.
If precision is too low → Technically possible, but operationally infeasible.
Assess this with business stakeholders: "False alarms will increase N-fold at this level. Can you accept that?"
Are there enough defect samples? — Sample size also sets a ceiling

With only 20 defect samples, a model struggles to generalize their patterns to meet a demand for 95% recall.

• Fewer than 100 defect samples → High recall targets are unstable. Collect additional data first.
• Oversampling methods such as SMOTE are supplements, rather than a fundamental solution.

What to tell business stakeholders: "We have N defect samples. Reaching the target requires at least M samples."

A three-step response to business requirements
Step 1 — Show the current model's PR curve first

"With recall set to 90%, the current model achieves precision of X%."
Present numbers to start the discussion. Share the current situation before judging feasibility.

Step 2 — State the constraints preventing the target

"With only N defect samples, precision drops below X% at 95% recall."
"Defective and normal feature distributions overlap in some regions, creating a data-level limit."
— Make clear that these are structural limitations of the data or the problem itself rather than simply a model issue.

Step 3 — Explain feasible conditions or alternatives

"Collecting at least N additional defect samples could bring us closer to the target."
"Reducing the recall target from 95% to 90% lets us maintain precision of X%."
"A two-stage inspection process (first model → detailed inspection of suspicious samples only) could meet the target."
— Rather than ending with "It cannot be done," explain what would need to change to make it possible.

Discussion question 4
"A business stakeholder says, 'We need recall of at least 95% to use this operationally.' The current model has recall 78% and PR-AUC 0.41. How would you respond?"
05 Metric limitations & comparison with operational criteria 10 min
Three cases where a model fails despite good metrics
  • ✕
    ① Range-specific bias — Systematic errors in important regions
    Overall R² may be 0.93 while RMSE is three times higher only below 70% yield (the high-risk region). Aggregate metrics dilute high-risk errors because most cases are normal. → Measure RMSE and recall separately by range.
  • ✕
    ② Process changes — Metrics reflect the training data
    R² 0.91 describes performance "under conditions similar to training." The same model can perform very differently after equipment replacement, material changes, or seasonal shifts. → Remeasure performance regularly. Treat a sudden metric drop as a possible signal of process change.
  • ✕
    ③ Data leakage — Excellent metrics warrant scrutiny
    If a feature is measured only after a defect occurs, the model learns as though it "already knows the answer." Even AUC 0.99 and recall 98% can describe an unusable model. Training R² of 0.99 versus test R² of 0.72 strongly suggests leakage or overfitting.
Comparison with operational criteria — Cpk / Ppk vs ML metrics
Process capability metrics — Cpk / Ppk

Question: "Does the process remain within specification limits?"

Cpk = min(USL-μ, μ-LSL) / (3σ)
→ Includes how far the process center deviates from the specification midpoint

Cpk ≥ 1.33 → Generally acceptable
Cpk < 1.0 → Out-of-spec cases may occur

Ppk uses overall variation (σ_overall) rather than short-term variation (σ_within) → More conservative

ML performance metrics — RMSE / recall

Question: "How well does the model predict actual values?"

RMSE = average magnitude of prediction error
Recall = how completely defects are detected

"Good model performance" ≠ "A stable process"
"High process Cpk" ≠ "No need for an ML model"

The two criteria answer different questions.

Good ML metrics can coexist with poor Cpk/Ppk — Why?

Predicting y well does not automatically improve Cpk/Ppk.

The reason is simple. The y predicted by the model may not be connected to Cpk/Ppk.

For example, achieving "yield prediction RMSE 1.2%" says nothing by itself about how yield relates to specification limits (USL/LSL).
If the model fits the average range but systematically fails in the extremes where specification violations occur, Cpk remains low.

Solution — Connect y to operational metrics

To improve both ML metrics (RMSE, recall) and operational metrics (Cpk, Ppk),
defining y appropriately from the outset is essential.

Poor target definition: "Predict average yield."
→ Low RMSE does not address specification violations → No Cpk improvement.

Appropriate target definition: "Predict specification violations" or "predict deviations from specification."
→ Better predictions reduce specification violations → Direct connection to Cpk/Ppk improvement.

When defining y, first ask: "What operational change follows if we predict this y well?"
Before building a model with strong ML metrics, define a y connected to operational metrics..

Why metrics need translation for business stakeholders

"RMSE is 1.8%." → Stakeholder: "Is that good?"
"Under the Cpk criterion, ±3σ = ±2.4%, and model error lies within that range." → Understandable

"Recall is 85%." → Stakeholder: "What does that mean?"
"We detect 85 of every 100 defects and let 15 pass through." → Understandable

The key is connecting the number to the operational cost structure, rather than stating a metric alone.

06 Interpretation practice — The trap of judging by numbers alone 5 min
For each scenario below, decide: "Can we use this model?"
Scenario A — Yield prediction regression model
Train R² = 0.97 / Test R² = 0.71 / MAE = 1.9% / RMSE = 5.1%
The gap between MAE (1.9%) and RMSE (5.1%) is large: very large errors occur intermittently. The train–test R² gap (0.26) is also large, strongly suggesting overfitting or leakage. Investigate the causes of these gaps before judging the metrics themselves.
Hold deployment — Investigate the train–test gap
Scenario B — Defect detection classifier
Accuracy = 98.2% / Precision = 72% / Recall = 51% / ROC-AUC = 0.94 / PR-AUC = 0.43
Recall 51% misses about half of actual defects. ROC-AUC (0.94) looks good but is overoptimistic on imbalanced data. PR-AUC (0.43) reflects practical performance. If escaped defects are costly, this model is difficult to use operationally.
Unsuitable — Recall is below the acceptable criterion
Scenario C — Defect detection classifier (after improvement)
Accuracy = 95.1% / Precision = 48% / Recall = 92% / PR-AUC = 0.71
Accuracy is lower than in B, but recall has risen to 92%, detecting 92% of defects. Low precision (48%) increases false alarms. The decision depends on whether escaped defects or false alarms are more costly. In most defect detection scenarios, C is much better than B.
Conditionally suitable — Confirm acceptance of false-alarm costs with stakeholders
The message running through this week's session

Metrics are a model assessment's starting point rather than its conclusion.

Questions to ask when metrics look good:
→ "Which ranges fit well? What about the important ranges?"
→ "How large is the train–test performance gap?"
→ "For imbalanced data, have we examined PR-AUC rather than just AUC?"
→ "Are these recall/precision levels acceptable within the operational cost structure?"

You must be able to translate metric values into operational language.

Q1. Is AUROC → PR-AUC → recall → train–test gap a useful interpretation sequence in practice?

A sequence is useful, but considering the metrics together is more appropriate.

AUROC and PR-AUC both examine how X and Y change as the threshold varies from 0 to 1. Both assess overall discrimination. It is natural to examine them together, then fix a threshold and check recall/precision.

Check overfitting/leakage afterward, using specific criteria.
A train–test AUC gap of 0.1 or more is a practical reason to suspect overfitting or leakage. Inspect that numerical gap before making a subjective judgment that performance is "too good to explain."

Q2. If more data do not improve performance, how can we distinguish a data problem from a model problem?

First examine "how X relates to y."

Before adding data, analyze which cases the current model misses. Regression tends to struggle with extremes, and classification with minority classes. Concentrated errors under certain operating conditions, times, or equipment reveal which data are missing.

The best additions contain X that explains y well. In manufacturing, however, defect data arise only when defects occur, making active selection difficult. First look for existing features related to y. A practical starting point is to ask domain experts, "What operating conditions differed before this defect occurred?"

To assess a model problem, distinguish inherent structural limits from adjustable factors such as HPO. HPO cannot resolve a model's structural limits; the data representation or the model itself must change.

Q3. What if the PR curve gives an optimal threshold but precision is too low for operational use?

Rather than calling a library's predict directly, obtain probabilities with a method such as predict_proba and adjust the threshold yourself.

Improving the model's discrimination takes priority over adjusting thresholds. First improve its ability to output defect probabilities close to 0 for normal cases and close to 1 for defects.

If precision is still too low for operational use after improving that ability, the model produces too many FP. There are two data-focused responses.

First, analyze regions with many FP. Examine normal samples mistaken for defects to identify cases with ambiguous boundaries. Review their labels or collect additional features that distinguish this region better.

Second, consider a two-stage process. The first model emphasizes recall with a broad screen; the second inspects only cases flagged by the first. This structure is used operationally when one model cannot meet precision and recall requirements simultaneously.

Q4. Does high performance such as ROC-AUC 0.99 always mean leakage? How can leakage be prevented, and what patterns occur in practice?

ROC-AUC 0.99 does not necessarily mean leakage. It can occur when training and test distributions differ little.

The clearest criterion is the train–test performance gap. Train AUC 0.99 and test AUC 0.97 are fine. Train AUC 0.99 and test AUC 0.71 strongly suggest leakage or overfitting.

Preventing leakage requires understanding each feature. The key question is whether it can be collected before the target value is determined. Leakage occurs when training includes information unavailable at inference time.

Common practical patterns include variables created only after the target is determined, test information mixed into full-dataset preprocessing statistics (mean, standard deviation), and future observations included in time-series training.

Q5. If RMSE is high in a specific range, should data in that range receive higher weights?

That approach is inappropriate. Penalizing errors there more heavily can bias learning toward that range and reduce performance elsewhere. The effect also depends on the model.

The appropriate first step is finding why the model fails in that range.

• Check whether there are enough training samples in the range. If samples are insufficient, collect more data from that range.
• Check for feature patterns specific to the range. If a variable explaining the range is missing, identify additional relevant features.
• Only after ruling out data and feature problems should you change the model structure or build separate models for different ranges.
