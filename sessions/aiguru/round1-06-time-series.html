Week 5 session summary

Some results cannot be trusted even when model performance looks good.
Leakage (future information), bias (toward particular ranges), distribution shift (changed data after deployment), and overfitting (fitting only training data).

Shared assessment principle:
❌ "Test R² 0.95 → This model is trustworthy."
✅ "Check the train–test gap → Inspect residual patterns → Review training-data composition → Then examine the numbers."

The essence of leakage

Future information in training makes performance unusually high. It is the leading cause of sudden performance drops after deployment, and especially common in this week's topic: time series.

Distribution shift

Changing operating conditions or seasonality makes data distributions differ between training and prediction. In time series, this occurs structurally.

Connection to this week

01 What is a time series? — Order ≠ time series 10 min
Key question: "Is there temporal dependence between rows?" Does one row affect the next? Data are not automatically a time series just because they accumulated in order.
Defining time series — Dependence rather than order

A time series consists of data recorded in chronological order.
However, "loaded in order" does not mean "a time series."

The real criterion is: Does a previous observation affect a subsequent one?
If that dependence exists, treat the data as a time series.
Without it, chronologically accumulated data can be treated as ordinary tabular data.

Common misconception — "Data accumulated in order are a time series."

Manufacturing data are usually loaded chronologically.
However, inspection results ordered by lot number are not necessarily a time series.

Lot 001 → Lot 002 → Lot 003…
If each lot was produced independently → Changing their order does not change the model results.
These are ordinary tabular data rather than a time series.

Conversely, continuous batches on the same machine can accumulate heat, wear, or continued material use,
so one lot's conditions can affect the next. In this case, the data form a time series.

Criteria — Which data are a time series?
Data typeTime series?Reason
Continuous-process sensor logs (1-second intervals) ✅ Time series Temperature at t-1 directly affects temperature at t. Continuity and autocorrelation exist.
Lot-level inspection results — Equipment resets between lots ❌ No Each lot starts independently. Earlier lot results do not affect the next lot.
Lot-level inspection results — Continuous operation on the same equipment ⚠️ Check required Heat accumulation or wear creates dependence between lots → Treat as a time series.
Batch process (each batch independent) ❌ Not between batches Within-batch data are a time series. Between independent batches, order is irrelevant.
Customer order history (loaded chronologically) ⚠️ Depends on the purpose Time series for demand forecasting; ordinary data for customer-feature analysis.
Problems when independent data are treated as a time series

Adding lag variables to independent lot data
→ Introduces meaningless variables.
→ Creates the illusion that lag_1 has high feature importance.
→ The model learns patterns that do not actually exist.

Problems when dependent data are treated as ordinary data

A random split of dependent observations
→ Creates leakage (future lots enter training).
→ Makes the model miss equipment-aging patterns.
→ Causes sudden performance degradation after deployment.

Assessment exercise
"Think of a dataset from your process. Could the value in a previous row affect the next row? If so, through what mechanism?"
Key characteristics of time series
CharacteristicExplanationManufacturing exampleImpact
Autocorrelation Current values are related to previous values. This hour's temperature tends to resemble the previous hour's. Past values should be used as features.
Trend Long-term increase or decrease Vibration readings gradually increase as equipment ages. The model should not mistake a trend for a stable pattern.
Seasonality Patterns repeating at regular intervals Higher cooling-water temperature in summer; quality differences across shifts Check whether validation includes the same seasons.
Non-stationarity Statistical properties change over time. Sensor distributions change after operating-condition adjustments. Training and deployment distributions differ, reducing performance.
02 Differences from ordinary data — What changes? 15 min
Even the same RandomForest creates problems if applied unchanged to time-series data. Let us examine why.
Difference 1
The independence assumption breaks down.
Most ML models assume that rows (samples) are independent. Time series violate this assumption.

Linear regression, trees, and XGBoost all assume "today's defect rate is unrelated to yesterday's."
In process data, however, consecutive observations are strongly related.

Breaking this assumption creates two problems.
① The model cannot exploit temporal patterns → Lower prediction accuracy.
② Validation overestimates real performance → Untrustworthy numbers.

Ordinary ML approach
Ignore row order. Learn only "today's defects = f(temperature, pressure)."
Time-series approach
Include historical features: "today's defects = f(temperature, pressure, yesterday's defects, 3-day mean temperature)."
Difference 2
Input features must be constructed differently.
In time series, "summaries of past patterns" matter alongside "current values."

Useful feature types:

Lag features: Values at t-1, t-2, etc. "Yesterday's temperature" helps predict "today's defects."
Rolling statistics: Mean, standard deviation, and maximum over the latest N observations. Capture patterns such as "rising mean temperature over the past hour."
Time features: Shift, day of week, time since equipment startup, etc.

However, creating these features with future observations causes leakage.

Leakage example
Incorrectly compute a lag from t+1 → Predict the present using the future.
Correct approach
Always ask when constructing a feature: "Is this information available at this time?"
Lag features / rolling statistics
Difference 3
Validation must be different.
Applying ordinary ML random splits to time series structurally creates leakage.

The most common mistake: Directly apply sklearn's train_test_split(shuffle=True)to time-series data.

Random shuffling can put December 2024 in training and June 2024 in testing.
The model predicts the past after already seeing the future.
This yields "unusually high performance" that differs substantially from post-deployment performance.

Incorrect (random split)
Ignore order and split randomly → Future data enter training.
Correct (time-based split)
Training before a cutoff and testing afterward → Chronological order is preserved.
03 Time-series leakage — Where future information enters 15 min
Key point: Time-series leakage is unintentional. "Incorrect code with surprisingly good results" is a leakage signal.
Why time-series leakage is dangerous

Leakage occurs in ordinary ML too, but in time series, a single line of incorrect code can cause it structurally.

Why it is particularly dangerous:
• Excellent performance metrics → False confidence
• Sudden performance collapse after deployment → Difficult diagnosis
• Residual plots may look normal → Visual inspection can mislead too.

Types of time-series leakage
Type 1
Scaling / normalization leakage
Fitting StandardScaler on all data lets test statistics influence training.

How it happens:
Apply MinMaxScaler().fit_transform() to the combined train and test data.
→ The scaler already knows the test minimum and maximum.
→ Future (test) statistics affect training transformations.

Correct approach:
.fit() on training only → .transform() on both training and test

Incorrect code
scaler.fit_transform(X_all) → split
Correct code
split → scaler.fit(X_train) → scaler.transform(X_test)
Type 2
Incorrect ordering of rolling / lag feature construction
Rolling statistics computed over the full dataset may incorporate test-time information in training-time features.

How it happens:
Compute rolling(window=7).mean() on the full DataFrame, then split.
→ If the window at t includes t+1 or t+2, future information leaks.

Caution:
pandas rolling() uses only past observations by default,
but center=True includes both preceding and following values → Future leakage.

Unsafe code
df['rolling_mean'] = df['temp'].rolling(7, center=True).mean()
Safe code
df['rolling_mean'] = df['temp'].rolling(7).mean() (default: past values only)
Type 3
Target encoding / aggregated-feature leakage
Occurs when features derived from the outcome (y) are used as inputs.

How it happens:
Use "equipment A's average defect rate" as a feature, calculated across the full period.
→ The "average defect rate" already incorporates test-period outcomes.

Manufacturing example:
When using "mean yield over the past month," respect the boundary between training and prediction periods.

Unsafe
Full-period statistics → Include future observations.
Safe
Aggregate only observations before prediction → Use an expanding window.
Discussion question
"If your process currently uses a prediction model, how can you verify that future information did not enter the training data?"
04 Time-based validation — What makes validation sound? 20 min
With incorrect validation, performance numbers themselves are untrustworthy. How the data are split is central to model evaluation.
❌ Incorrect: Random split
Split the full dataset randomly — Chronological order is mixed.
Test (Jun)
Train (Dec)
Train (Mar)
Test (Sep)
Train (Nov)
Test (Jan)
Train (Aug)
⚠ December enters training → Future information is already known when predicting test cases from January and June.
✅ Correct: Time-based split
Split before/after a cutoff — Preserve order.
Train (Jan–Sep 2024)
Test (Oct–Dec 2024)
✓ Training always precedes testing. The model predicts the future using only the past.
Walk-forward validation (time-series cross-validation)
Fold 1
Train
Val
Unused
Fold 2
Train (includes previous folds)
Val
Unused
Fold 3
Train (includes previous folds)
Val
Unused
The training window expands. Validation always follows training. Unlike ordinary K-fold, chronological order is never violated.
Validation-method comparison
MethodSuitability for time seriesLeakage riskWhen to use
Random Split Unsuitable High — Future observations enter training. Ordinary ML (images, independent tabular data)
Time-based Split Suitable None Basic time-series validation with sufficient data
Walk-forward Most suitable None Check performance stability and simulate real operations.
K-fold Unsuitable High — Ignores order. Never use for time series.
Practical checklist

Always check when reviewing model-validation reports or code:

□ Was shuffle=False explicitly set in train_test_split?
□ Or were data split manually using a time cutoff?
□ Was the scaler fitted only on training and applied to test with transform?
□ Do rolling/lag features exclude future values?
□ Is the train–test gap reasonable? (An unusually small gap warrants scrutiny.)

04+ Training windows and retraining frequency — How to choose 15 min
Key point: These are often chosen intuitively, such as "the most recent year" or "100,000 records." The decision needs evidence, and that evidence must come from the data.
① Training window — How far back should the data go?
Why it matters

Too short — Seasonality and unusual events are not learned; the model is unstable.
Too long — Obsolete operating conditions enter training and can reduce performance.

Key question: Do present and past processes follow "the same patterns"?
A recipe revision, equipment replacement, or material change makes earlier observations data from a different process.

Evidence for choosing the window — Three analyses
Analysis 1
Check process stability — When did the current process begin?
Check this first. If the process changed, normally exclude earlier data.

How to check:
Review change histories (recipe versions, equipment replacement dates, material changes).
Plot the series and locate abrupt changes in mean or variance.
Compare monthly/quarterly distributions with overlaid histograms.

Decision: As a rule, train only on data after the distribution-change point.
Use earlier data only for reference, or include them with an explicit process-change flag.

Practical guideline
Without process changes → At least 1–2 years. With seasonality, include at least one full year.
Common mistake
Unknowingly using data from three years ago across process changes → Mixing different process patterns.
Analysis 2
Walk-forward performance curve — Does a longer training window improve performance?
Measure performance as the training window grows. The point where improvement stops is the appropriate window.

Adapt walk-forward validation.
Expand training from 3 months → 6 months → 1 year → 2 years, measuring test performance at each length.

Three interpretation patterns:

① Continued improvement — More data help. Use the longest feasible window.
② Plateau after a point — That point defines the appropriate window. Earlier data provide no extra benefit.
③ Improvement followed by decline — Data before a certain point act as noise. Use only the more recent window.

Value of this analysis
Choose the window from data rather than intuition. Provide evidence for "Why one year?"
Limitation
If the process changed, verify stability before this analysis.
Analysis 3
Balance with the forecast horizon — How far ahead?
There is an empirical relationship between forecast horizon and training-window length.

A longer forecast horizon requires more training data.

Yield one hour ahead → A few recent days or weeks may suffice.
Next month's production → At least 1–2 years (including seasonality).
Demand six months ahead → Three years or more may be needed.

Empirical guideline: Training-window length ÷ forecast horizon ≥ 10
Forecasting one month ahead → At least 10 months of training data.
This is a starting point, not an absolute rule. Validate it with Analyses 1 and 2.

Practical sequence
Check process stability → Set a minimum window from the horizon → Determine the actual window with walk-forward validation.
Avoid
Using "as much as possible" without considering the horizon, or using too short a window relative to the horizon because data are scarce.
② Retraining frequency — When should the model learn again?
Why retraining is needed

A model knows only the patterns present during training.
Gradual process changes, seasons, or equipment aging create situations the model has not seen.
Continued use without retraining can cause gradual or sudden performance loss.

Key question: How can we tell whether "this model is still valid"?

Choosing retraining frequency — Three approaches
MethodHowAdvantagesDisadvantages / cautions
Scheduled retraining
Monthly, quarterly		 Retrain at fixed calendar intervals. Simple management; predictable. Too late for rapid process changes; unnecessary when conditions remain unchanged.
Performance-monitoring based
Recommended		 Monitor actual prediction errors continuously → Retrain when errors exceed a threshold. Retrain only when needed; respond immediately to degradation. Requires monitoring infrastructure; thresholds can be difficult to set.
Event-based Retrain immediately after process changes, equipment replacement, or material changes. Fastest response to distribution shift. Requires managed change histories; small changes are harder to assess.
Monitoring-based retraining — Concept
How to set the threshold

Use initial deployment test performance as the baseline.

Example: Deployment RMSE = 2.1 → Threshold = 3.0 (retrain after deterioration of 50% or more).

Or use a business criterion: If "yield errors over 5 percentage points disrupt operations,"
set the RMSE threshold to 5.

There is no universal answer. Business impact is the most practical basis.

Which data should retraining use?

Rolling window: Always use only the latest N months; discard older data.
→ Suitable for rapidly changing processes or when old data add noise.

Expanding window: Keep accumulating data from the beginning.
→ Suitable when more data improve performance and the process is stable.

Choose according to the pattern established in Analysis 2 (walk-forward performance curves).

Recommended sequence — From initial model development to retraining

Step 1 — Review process-change histories → Determine the training start date.
Step 2 — Check the forecast horizon → Set the minimum training window.
Step 3 — Compare window lengths with walk-forward validation → Finalize the appropriate window.
Step 4 — Establish post-deployment prediction-error monitoring.
Step 5 — Trigger retraining when a threshold is exceeded or a process-change event occurs.
Step 6 — Reset the retraining window using the appropriate rolling or expanding strategy.

Discussion question
"A deployed model's performance is gradually declining. What should you check before deciding to retrain? How would you distinguish process change from ordinary noise?"
05 Manufacturing × time series — Practical precautions 15 min
Most manufacturing-process data are time series, yet are often treated as ordinary ML data. Let us examine the resulting problems.
Special cases in manufacturing time series
Process-change events

Recipe revisions, equipment replacement, and material-lot changes can sharply alter data distributions.

Problem: A model trained before the change cannot predict afterward.

Response: Explicitly include process-change events as features, or use post-change data as the retraining baseline.

Sensor anomalies / missing values

Manufacturing sensors sometimes have missing intervals.

Problem: Simple interpolation (mean imputation) contaminates lag features.

Response: Add missingness indicators. Exclude intervals with high missing-value rates from training.

Synchronizing multiple sensor series

Sensors have different sampling intervals: temperature every minute, pressure every 10 seconds, quality by batch.

Problem: Aligning sensors with different intervals requires interpolation, introducing possible errors.

Response: Specify the reference sampling interval and interpolation method.

Batch vs continuous processes

Batches may be independent; continuous processes have strong temporal dependence.

Batch process: Within-batch time series + independence between batches
Continuous process: Conventional time-series analysis

Confusion leads to unnecessary lag features or ignored batch boundaries.

Interpretation scenario: Yield prediction — What went wrong?
Situation

A yield model uses XGBoost and data from all of 2024 (January–December).
Results: Train R² = 0.97, test R² = 0.95 — Excellent performance.
Real performance drops sharply after deployment in January 2025.

Diagnostic questions:
① How was train_test_split used? Random or time-based?
② Where was the scaler fitted?
③ Were rolling features computed on the full dataset first?
④ Do operating conditions differ between 2024 and 2025?

❌ If the design was wrong
Random split → December 2024 observations enter training.
Scaler fitted on all data → Test distributions already influence it.
→ R² 0.95 reflects a leakage illusion rather than real performance.
→ New 2025 data do not benefit from that leakage.
✅ Correct redesign
Time-based split: January–October train; November–December test.
Fit the scaler only on training data.
Rolling features use only observations before t.
→ Lower validation performance, but trustworthy numbers.
05+ Post-deployment input issues — What happens when variables change? 15 min
Key point: The model remembers its training input structure. If deployed inputs change—new values appear or variables disappear—it usually makes incorrect predictions silently.
Problem A — New categories appear

Categories absent from training arrive after deployment.

New equipment lines, material suppliers, product codes, and operator codes continually appear during operations.

In ordinary ML, all categories can be identified before deployment.
In time series, future category values are unknown.

Problem B — Variables disappear

A variable used in training disappears after deployment.

Sensor failures, stopped measurements, or system errors cause missing columns without warning.

The model expects the same input variables as during training.
A missing variable causes a shape mismatch or silent prediction errors.

Problem A — How encodings respond to new categories
Encoding methodWhen a new category arrivesResult
One-hot encoding No corresponding column exists. Error or all zeros → Interpreted as "none of the known categories."
Label encoding Arbitrarily assign an unseen number. Predict using a meaningless number without an error → Silent prediction errors
Target encoding No encoded value exists. NaN → Error or replacement with the overall mean
Responses to Type A
Approach 1 — Unknown bucket

Include an "OTHER/UNKNOWN" category during training.
New values → Assign to this bucket → No error.

✓ Simple implementation; immediately usable
✕ Does not capture the new category's characteristics

Approach 2 — Frequency encoding

Encode occurrence counts rather than category names.
New values → Automatically receive 0.

✓ Automatically handles new values; includes rarity information
✕ Does not capture the category's meaning

Approach 3 — Retraining trigger

Detect new categories as events.
Short term: Temporary handling with Approach 1 or 2
After sufficient data accumulate → Retrain.

✓ Most accurate over the long term
✕ Cannot respond immediately

Problem B — A variable disappears after sensor failure
Handling methodWhat happensRisk
Omit the column entirely. Input shape mismatch → Model error; no prediction. Detected immediately — Preferable to silent failure.
Pass the column filled with NaN. Runs without errors, but prediction quality falls. Model-dependent. Tree models may handle NaN.
Pass the column filled with 0. Zero is interpreted as an actual sensor reading. Silent prediction errors — Most dangerous; interpreted as, for example, temperature 0°C.
Use the last value (forward fill). Reasonable substitute for a short failure. Safe for a few observations; inappropriate for extended failures.
Performance impact by feature importance
Responses to Type B — According to failure duration
Failure durationRecommended responseReason
A few observations to a few hours
Temporary error		 Forward fill (retain the previous value) Sensor values are continuous; the previous value is a reasonable estimate.
Days to weeks
Extended failure		 Estimate with regression on correlated variables, or remove the variable and retrain. Forward-fill errors accumulate. Assess feature importance before deciding.
Permanent removal / measurement stopped Remove the variable and retrain. Continuously filling an absent variable with NaN/0 creates systematic prediction errors.
Shared principle — Input monitoring matters as much as performance monitoring
Input-data monitoring

Monitoring only post-deployment prediction errors is insufficient.
Monitor the inputs themselves before errors deteriorate.

Monitoring checks:
□ Are categories absent from training arriving?
□ Has a column's NaN rate suddenly increased?
□ Do feature distributions differ greatly from training? Compare means and standard deviations.
□ Has the input shape (number of columns) changed?

If any occurs → Send an alert before prediction errors deteriorate.

Discussion question
"A key temperature sensor suddenly fails. It ranks first in feature importance and will take three days to repair. How would you operate the model during those three days?"
06 Interpretation practice — Explaining time-series results 20 min
Even without writing code, you should be able to assess and explain whether reported results are trustworthy.
Example scenario: The AI team reports the following
Report

Model: XGBoost
Data: Sensor data from 2023–2024 (24 months)
Features: Temperature, pressure, flow, current, rolling_mean_7days, lag_1
Validation: 80/20 random split
Train R²: 0.96 / Test R²: 0.94
Conclusion: "High-accuracy yield prediction is possible. Immediate deployment recommended."

What you should check
  • ✕
    "80/20 random split" — Random splitting of time series
    If 24 months were shuffled randomly, 2024 observations enter training and 2023 observations testing. This predicts the past using the future. R² 0.94 cannot be trusted.
  • ✕
    rolling_mean_7days — Check the calculation order
    If rolling statistics were computed on the full dataset before splitting, observations near the split boundary may be contaminated even without center=True. Inspect when the rolling calculation occurred.
  • !
    Train R² 0.96 vs test R² 0.94 — The gap may be too small
    Training performance is normally higher than test performance. A 0.02 gap may indicate leakage inflating test results, or a sufficiently simple model without overfitting. Examine both possibilities.
  • !
    2023–2024 data — Check for process-change events
    Recipe revisions, equipment replacements, or material changes over those two years may prevent an early-process model from representing the later process correctly.
  • ✓
    lag_1 — Incorporating temporal structure is appropriate
    However, check whether lag calculation occurred after splitting. Properly computed lag features likely contain meaningful information.
Appropriate feedback

❌ "These results are wrong. I do not trust them."

✅ "I suggest redesigning validation around a time cutoff. A random split was used, but time-series validation should preserve chronological order to estimate real operational performance. Revalidate with months 1–20 for training and 21–24 for testing. R² may fall below 0.94, but it will be closer to actual performance."

Group discussion (key exercise)
"Time-based revalidation lowers R² from 0.94 to 0.78. How would you interpret this and report it to management? Has the model become worse, or have we obtained a more honest number?"
06+ Time-series models vs ordinary ML — Which to use? 25 min
Key question: "Does time series mean we should use ARIMA?" There is no universal answer. It depends on the problem. The goal is to learn how to decide.
Dedicated time-series models

Examples: ARIMA, SARIMA, Prophet, Exponential Smoothing

Core principle: "Predict the future from patterns in past values."
Mathematically model y's temporal structure (trend, seasonality, autocorrelation).

Input: One series of y (or a small number of external variables)
Strengths: Works without external variables. Intuitive interpretation. Provides uncertainty intervals.
Weaknesses: Limited handling of external factors (operating-condition changes). Weaker with many variables.

Ordinary ML + time-series features

Examples: XGBoost + lag/rolling features; LinearRegression + time-series features

Core principle: "Represent past patterns as features for an ordinary model."
Design features such as lag_1 and rolling_mean_7 and feed them into existing models.

Input: Combine y's lag/rolling features with external variables (temperature, pressure, equipment conditions, etc.).
Strengths: Uses external factors and temporal patterns together. Strong with many variables.
Weaknesses: Requires manual feature design. Leakage risk. No uncertainty intervals.

Dedicated time-series models — ARIMA intuition
ARIMA
AR + I + MA — Three mechanisms combined
Combine past values, past errors, and differencing to predict the next observation.

AR (autoregressive) — Predict from the series' own past values
"Today's temperature = yesterday's temperature × 0.7 + the day before's × 0.2 + a constant."
Useful when the previous value strongly affects the next, as with stocks or sensor signals.

I (integrated) — Remove trends through differencing
If values keep increasing → Transform them into "current value - previous value" (the change).
Changes fluctuate within a stable range without the trend → Easier to learn.

MA (moving average) — Correct with past prediction errors
"Current prediction error = previous prediction error × a weight."
Helps correct values after sudden shocks (events).

Works well when
y has strong, recurring patterns, or only a series without external variables is available.
Works poorly when
External factors such as operating-condition changes determine y, or many explanatory variables exist.
Ordinary ML + time-series features — "Design the variables yourself."
ML + Lag/Rolling
Manually turn temporal patterns into features for existing models.
A person constructs features for what ARIMA handles automatically through equations.

Implement ARIMA's AR effect through lag features: lag_1 = y(t-1), lag_2 = y(t-2)
Represent ARIMA's trend effect through rolling statistics: rolling_mean_7 = mean of the latest 7 observations
Other inputs → Operating conditions, equipment status, time, day of week, etc. External variables are included together.

Feed the resulting feature table directly into XGBoost or LinearRegression.
To the model, it is "just a numerical table": it does not know the data are a time series.

Key advantage: External variables and temporal patterns can be represented together.
Combining controllable variables such as temperature and pressure with past yield patterns is an advantage in manufacturing.

Works well when
When external operating variables explain y strongly, many variables exist, or an existing ML pipeline can be reused.
Cautions
Feature-design errors → Leakage. Without external variables and with purely temporal patterns, ARIMA is simpler and safer.
Which approach to choose — Decision criteria
CriterionDedicated time-series models (e.g., ARIMA)Ordinary ML + time-series features
Are external variables available? None or few → Suitable More variables → Stronger
Are y's own patterns strong? Stronger patterns → More suitable (high autocorrelation) External variables can compensate for weak temporal patterns.
Are uncertainty intervals needed? Built in (confidence intervals) Not built in (additional implementation needed)
Can process changes / events be represented? Limited (Prophet supports some) Add them directly as features.
Ease of interpretation Parameters have clear meanings. Indirectly inspect feature importance.
Data volume Works with limited data. Needs sufficient data to construct lag/rolling features.
Leakage risk Handled internally → Low Feature-design mistakes → High
Full flow: Model selection → Training window → Retraining
Decisions by manufacturing scenario
ScenarioRecommended approachReason
"I want to predict yield next hour. We have 20 sensors." ML + features Many external variables (20 sensors). XGBoost + lag_1–3 + rolling features.
"I want to forecast monthly production six months ahead. We have production history but no process data." SARIMA / Prophet No external variables; clear monthly seasonality. Use y's own patterns only.
"I want early equipment anomaly detection. Vibration and current sensors are available." ML + features Combine multivariate sensors and anomaly patterns. Add rolling std (a sharp rise in standard deviation) as a feature.
"I want to forecast incoming material quantities to optimize ordering." SARIMA → ML Start with SARIMA for seasonality. Extend to ML when adding supplier or price variables.
Practical advice — Try both

Choosing "ARIMA or XGBoost" from theory alone is difficult.
In practice, run both and compare performance as the standard approach.

Use exactly the same validation method: Evaluate both with time-based splits.
Comparing time-based ARIMA with randomly split XGBoost unfairly favors XGBoost.

Discussion question
"For a metric you need to predict in your current work, name one approach you would use based on whether external variables are available."
07 Wrap-up & Q&A 10 min
Week 6 key message

Time-series data are "data where row order has meaning."
Ignoring that property overestimates performance and causes degradation after deployment.

Remember four things:

1. Always validate by time. — Never use random splits for time series.
2. One line of code can create leakage. — Check the order of scaler, rolling, and lag operations.
3. Check validation before performance numbers. — Even R² 0.95 is meaningless with leakage.
4. External variables are the first model-selection criterion. — Available: ML + features. Absent: Dedicated time-series models.
