Week 5 세션 요약

모델 성능이 좋아 보여도 신뢰할 수 없는 경우가 있습니다.
Leakage(미래 정보 유출), Bias(특정 구간 편향), 분포 변화(배포 후 데이터가 달라짐), 과적합(학습 데이터에만 맞춤).

공통 판단 기준:
❌ "Test R² 0.95 → 이 모델 믿을 수 있다"
✅ "Train과 Test 차이 확인 → 잔차 패턴 확인 → 학습 데이터 구성 확인 → 그 다음 숫자를 본다"

Leakage 핵심

미래 정보가 학습에 들어가면 성능이 비정상적으로 높아집니다. 실제 배포 후 성능이 갑자기 떨어지는 원인 1순위입니다. 이번 주 시계열에서 가장 자주 발생합니다.

분포 변화

공정 조건이 바뀌거나 계절성이 있으면 학습 시점 데이터와 예측 시점 데이터의 분포가 달라집니다. 시계열에서는 이것이 구조적으로 발생합니다.

01 시계열이란 무엇인가 — 순서 ≠ 시계열 10 min
핵심 질문: "행 간에 시간 의존성이 있는가?" — 이전 행의 값이 다음 행에 영향을 주는가. 순서대로 쌓였다고 자동으로 시계열이 되지는 않습니다.
시계열의 정의 — 순서가 아니라 의존성

시계열(Time Series)은 시간 순서대로 기록된 데이터입니다.
그런데 "순서대로 적재됐다"는 것과 "시계열이다"는 같은 말이 아닙니다.

진짜 기준은 하나입니다 — 이전 시점의 값이 다음 시점에 영향을 주는가.
이 의존성이 있으면 시계열처럼 다뤄야 합니다.
없으면 순서대로 쌓였어도 일반 표 데이터로 다뤄도 됩니다.

흔한 오해 — "순서대로 쌓이면 시계열이다"

제조 현장에서 데이터는 대부분 시간 순서로 적재됩니다.
그런데 Lot 번호 순서로 쌓인 검사 결과가 반드시 시계열은 아닙니다.

Lot 001 → Lot 002 → Lot 003…
각 Lot이 서로 독립적으로 생산됐다면 → 순서를 바꿔도 모델 결과가 달라지지 않습니다.
이 경우는 시계열이 아니라 그냥 표 데이터입니다.

반대로 같은 설비에서 연속으로 돌아가는 배치라면 → 열 누적, 마모, 원자재 연속 사용으로 인해
이전 Lot 조건이 다음 Lot에 영향을 줄 수 있습니다. 이 경우는 시계열입니다.

판단 기준 — 어떤 경우가 시계열인가
데이터 유형시계열?판단 근거
연속 공정 센서 로그 (1초 간격) ✅ 시계열 t-1 온도가 t 온도에 직접 영향. 연속성·자기상관 있음
Lot별 검사 결과 — Lot 간 설비 초기화 ❌ 아님 각 Lot이 독립적으로 시작. 이전 Lot 결과가 다음 Lot에 영향 없음
Lot별 검사 결과 — 같은 설비 연속 가동 ⚠️ 확인 필요 설비 열 누적·마모가 있으면 Lot 간 의존성 발생 → 시계열처럼 다뤄야
배치 공정 (각 배치 독립) ❌ 배치 간은 아님 배치 내부는 시계열. 배치 간은 독립이면 순서 무관
고객 주문 이력 (시간순 적재) ⚠️ 목적에 따라 수요 예측이 목적이면 시계열. 고객 특성 분석이면 일반 데이터
시계열로 잘못 다룰 때 문제

독립적인 Lot 데이터에 Lag 변수를 추가하면
→ 실제로는 의미 없는 변수가 모델에 들어감
→ Feature importance에 lag_1이 높게 잡히는 착시
→ 모델이 실제 없는 패턴을 학습

일반 데이터로 잘못 다룰 때 문제

의존성이 있는 데이터를 random split하면
→ Leakage 발생 (미래 Lot이 Train에 포함)
→ 설비 노후화 패턴을 모델이 놓침
→ 배포 후 성능이 갑자기 저하

판단 연습
"우리 공정의 데이터를 하나 떠올려 보세요. 그 데이터에서 이전 행의 값이 다음 행에 영향을 줄 가능성이 있나요? 있다면 어떤 메커니즘으로요?"
시계열의 핵심 특징
특징설명제조 예시영향
자기상관 (Autocorrelation) 지금 값이 이전 값과 연관됨 이번 시간 온도는 이전 시간 온도와 비슷한 경향 과거 값을 변수로 사용해야 함
추세 (Trend) 장기적으로 증가 또는 감소 설비 노후화로 진동 수치가 서서히 상승 모델이 추세를 "패턴"으로 학습하면 안 됨
계절성 (Seasonality) 일정 주기로 반복되는 패턴 여름철 냉각수 온도 상승, 교대 시간대별 품질 차이 검증 시 같은 계절 포함 여부 확인
비정상성 (Non-stationarity) 시간에 따라 통계적 특성이 변함 공정 조건 변경 후 센서 분포가 달라짐 학습-배포 시점 분포가 달라 성능 저하
02 일반 데이터와의 차이 — 무엇이 달라지는가 15 min
같은 RandomForest를 쓰더라도, 시계열 데이터에 그대로 적용하면 반드시 문제가 생깁니다. 왜 그런지 구체적으로 확인합니다.
차이 1
독립성 가정이 깨진다
대부분의 ML 모델은 각 행(샘플)이 서로 독립이라고 가정합니다. 시계열은 이 가정을 위반합니다.

선형회귀, 트리, XGBoost 모두 "오늘의 불량률과 어제의 불량률은 관계없다"고 가정합니다.
하지만 공정 데이터에서 연속된 시점은 서로 강하게 연관됩니다.

이 가정이 깨지면 두 가지 문제가 생깁니다.
① 모델이 시간 패턴을 활용하지 못함 → 예측 정확도 손실
② 검증 결과가 실제 성능보다 과대 추정 → 믿을 수 없는 숫자

일반 ML 방식
행 순서 무시. "오늘 불량 = f(온도, 압력)" 만으로 학습
시계열 대응 방식
과거 값을 변수로 추가. "오늘 불량 = f(온도, 압력, 어제 불량, 3일 평균 온도)"
차이 2
입력 변수를 다르게 구성해야 한다
시계열에서는 "지금 시점의 값" 외에 "과거 패턴을 요약한 값"이 중요한 변수가 됩니다.

시계열에서 유용한 변수 유형:

Lag 변수: t-1 시점 값, t-2 시점 값 등. "어제 온도"가 "오늘 불량"을 예측하는 데 도움이 됨.
Rolling 통계: 최근 N개 시점의 평균, 표준편차, 최댓값. "지난 1시간 평균 온도 상승" 같은 패턴 포착.
시간 특성: 교대 시간대, 요일, 설비 가동 후 경과 시간 등.

단, 이 변수들을 만들 때 미래 시점의 값을 사용하면 Leakage가 발생합니다.

Leakage 예시
t+1 시점 값을 Lag 변수로 잘못 계산 → 미래를 보고 현재 예측
올바른 방식
변수 생성 시 항상 "이 시점에서 알 수 있는 정보인가?" 확인
Lag 변수 / Rolling 통계 개념
차이 3
검증 방식이 달라야 한다
일반 ML의 무작위 분리(random split)를 시계열에 쓰면 Leakage가 구조적으로 발생합니다.

가장 흔한 실수: sklearn의 train_test_split(shuffle=True)를 시계열에 그대로 사용.

무작위로 섞으면 Train에 2024년 12월 데이터가 들어가고, Test에 2024년 6월 데이터가 들어갑니다.
모델은 미래를 이미 본 상태에서 과거를 예측하게 됩니다.
결과는 "비정상적으로 높은 성능" — 실제 배포 후 성능과 크게 괴리됩니다.

잘못된 방식 (Random Split)
순서 무시하고 무작위로 Train/Test 분리 → 미래 데이터가 Train에 포함
올바른 방식 (Time-based Split)
특정 시점 기준으로 앞은 Train, 뒤는 Test → 시간 순서 유지
03 시계열 데이터 누수 — 어디서 미래 정보가 들어오는가 15 min
핵심: 시계열 Leakage는 의도적이지 않습니다. "코드가 틀렸는데 결과가 너무 좋게 나오는" 상황이 Leakage의 신호입니다.
시계열 Leakage가 위험한 이유

일반 ML에서도 Leakage가 발생하지만, 시계열에서는 코드 한 줄 실수로 구조적으로 발생합니다.

특히 위험한 이유:
• 모델 성능 지표가 아주 좋게 나옴 → 잘못된 신뢰 형성
• 배포 후 성능이 갑자기 떨어짐 → 원인 파악이 어려움
• 잔차 플롯이 정상적으로 보일 수 있음 → 시각적으로도 속음

시계열 Leakage 발생 유형
유형 1
스케일링 / 정규화 Leakage
전체 데이터로 StandardScaler를 fit하면 Test 데이터의 통계가 Train에 영향을 줍니다.

발생 상황:
Train+Test 전체 데이터에 MinMaxScaler().fit_transform() 적용
→ Scaler가 Test 데이터의 최댓값/최솟값을 이미 알고 있음
→ Train 데이터 변환 시 미래(Test) 통계가 반영됨

올바른 방법:
Train에만 .fit() → Train과 Test 모두 .transform()

잘못된 코드
scaler.fit_transform(X_all) → split
올바른 코드
split → scaler.fit(X_train) → scaler.transform(X_test)
유형 2
Rolling / Lag 변수 생성 순서 오류
전체 데이터에서 Rolling 통계를 계산하면, Train 시점 데이터가 Test 시점 정보를 포함하게 됩니다.

발생 상황:
전체 DataFrame에 rolling(window=7).mean() 계산 후 split
→ 만약 t 시점에 t+1, t+2 데이터가 window에 포함되면 미래 정보 유출

주의할 점:
pandas의 rolling()은 기본적으로 과거 값만 사용하지만,
center=True 옵션을 쓰면 앞뒤 값을 모두 포함 → 미래 정보 유출

위험 코드
df['rolling_mean'] = df['temp'].rolling(7, center=True).mean()
안전한 코드
df['rolling_mean'] = df['temp'].rolling(7).mean() (기본값: 과거만)
유형 3
타겟 인코딩 / 집계 변수 Leakage
결과 변수(y)를 이용해 만든 변수를 입력으로 사용할 때 발생합니다.

발생 상황:
"설비 A의 평균 불량률"을 변수로 만들 때, 전체 기간 평균을 사용
→ Test 시점 불량률이 "평균 불량률" 변수에 이미 반영됨

제조 현장 예시:
"지난 1개월 평균 수율"을 변수로 쓸 때 → 학습 기간 vs 예측 기간 경계 주의

위험
전체 기간 통계 사용 → 미래 포함
안전
예측 시점 이전 데이터만으로 집계 → expanding window 사용
토론 질문
"우리 공정에서 지금 사용 중인 예측 모델이 있다면, 학습 데이터에 미래 정보가 들어가지 않았다고 어떻게 확인할 수 있을까요?"
04 시점 기반 검증 — 올바른 검증이란 20 min
검증 방식이 잘못되면 성능 숫자 자체가 신뢰할 수 없습니다. 어떻게 분리하느냐가 모델 평가의 핵심입니다.

모델 검증 보고서나 코드를 받았을 때 반드시 확인:

□ train_test_split에 shuffle=False를 명시했는가?
□ 또는 시점 기준으로 수동 분리했는가?
□ Scaler를 Train에만 fit하고 Test에 transform했는가?
□ Rolling/Lag 변수 생성 시 미래 값이 포함되지 않았는가?
□ Train 성능과 Test 성능 차이가 합리적인가? (너무 비슷하면 의심)

04+ 학습 데이터 범위와 재학습 주기 — 어떻게 결정하는가 15 min
핵심: "최근 1년치"나 "10만 건"처럼 직관으로 정하는 경우가 많습니다. 하지만 이 결정은 근거가 있어야 하고, 근거는 데이터에서 찾아야 합니다.
① 학습 데이터 범위 — 얼마나 오래된 데이터까지 쓸 것인가
왜 이게 중요한가

너무 짧게 잡으면 — 계절성, 비정상 이벤트를 못 배움. 모델이 불안정.
너무 길게 잡으면 — 이미 유효하지 않은 공정 조건이 학습에 섞임. 오히려 성능 저하.

핵심 질문: 지금 공정과 과거 공정이 "같은 패턴"인가?
레시피 변경, 설비 교체, 원자재 변경이 있었다면 — 그 이전 데이터는 다른 공정의 데이터입니다.

범위 결정 근거 — 세 가지 분석
분석 1
공정 안정성 확인 — 언제부터 지금과 같은 공정인가
가장 먼저 확인해야 합니다. 공정이 바뀐 시점이 있으면 그 이전 데이터는 원칙적으로 제외합니다.

확인 방법:
공정 변경 이력 조회 (레시피 버전, 설비 교체 일자, 원자재 변경 이력)
시계열 시각화 — 평균·분산이 특정 시점에 급격히 바뀌는 구간 찾기
월별·분기별 데이터 분포 비교 (히스토그램 겹쳐보기)

판단: "분포가 바뀐 시점" 이후 데이터만 학습에 사용하는 것이 원칙.
그 이전 데이터는 참고용으로만 쓰거나, 공정 변경 플래그를 변수로 추가해 함께 사용.

실무 기준
공정 변경 이력이 없다면 → 최소 1~2년치. 계절성이 있으면 반드시 1년 이상.
흔한 실수
공정 변경을 모른 채 3년 전 데이터까지 사용 → 다른 공정 패턴이 섞임
분석 2
Walk-forward 성능 곡선 — 학습 구간이 길어질수록 성능이 좋아지는가
학습 데이터를 늘려가면서 성능 변화를 직접 측정합니다. 성능이 더 이상 오르지 않는 지점이 적정 범위입니다.

Walk-forward 검증을 응용합니다.
학습 구간을 3개월 → 6개월 → 1년 → 2년으로 늘려가며 각각 Test 성능을 측정.

해석 패턴 3가지:

① 계속 오름 — 데이터가 많을수록 좋다. 가능한 최대 범위 사용.
② 일정 구간 후 정체 — 그 지점이 적정 범위. 이후 데이터는 추가 이득이 없음.
③ 오르다가 하락 — 어느 시점 이전 데이터가 노이즈로 작용. 그 시점까지만 사용.

이 분석의 가치
직관이 아니라 데이터로 범위를 결정. "왜 1년인가?" 에 근거를 댈 수 있음.
한계
공정 변경이 있으면 이 분석 전에 반드시 공정 안정성부터 확인해야 함.
분석 3
예측 목표 기간과의 균형 — 얼마나 앞을 볼 것인가
예측하려는 기간(horizon)과 학습 데이터 범위 사이에는 경험적인 비율이 있습니다.

예측 horizon이 길수록 더 많은 학습 데이터가 필요합니다.

1시간 뒤 수율 예측 → 최근 수일~수주치로도 충분할 수 있음
다음 달 생산량 예측 → 최소 1~2년치 필요 (계절성 포함)
6개월 뒤 수요 예측 → 3년 이상 필요할 수 있음

경험적 기준: 학습 데이터 길이 ÷ 예측 horizon ≥ 10
1개월 앞을 예측하고 싶다면 → 최소 10개월치 학습 데이터.
단, 이건 출발점이지 절대 기준이 아닙니다. 분석 1, 2로 검증해야 합니다.

실무 순서
공정 안정성 확인 → horizon 기준 최소 범위 설정 → Walk-forward로 실제 범위 결정
하지 말 것
horizon 고려 없이 "일단 많이" 쓰기. 또는 데이터 부족을 이유로 horizon 대비 너무 짧게 잡기
② 재학습 주기 — 언제 다시 학습해야 하는가
왜 재학습이 필요한가

모델은 학습한 시점의 패턴만 알고 있습니다.
공정이 조금씩 변하거나, 계절이 바뀌거나, 설비가 노후화되면 — 모델이 보지 못한 상황이 생깁니다.
재학습 없이 계속 쓰면 성능이 서서히, 또는 갑자기 떨어집니다.

핵심 질문: "이 모델이 지금도 유효한가?"를 어떻게 판단할 것인가.

재학습 주기 결정 방식 — 세 가지 접근
방식어떻게장점단점 / 주의
일정 주기 재학습
매월, 매분기		 달력 기준으로 고정 주기 재학습 관리 단순. 예측 가능 공정이 빨리 바뀌면 늦음. 바뀌지 않으면 불필요한 재학습
성능 모니터링 기반
권장		 실제 예측 오차를 지속 모니터링 → 오차가 임계값 초과 시 재학습 필요할 때만 재학습. 성능 저하 즉시 대응 모니터링 체계 구축 필요. 임계값 설정이 어려움
이벤트 기반 공정 변경·설비 교체·원자재 변경 발생 시 즉시 재학습 분포 변화에 가장 빠른 대응 변경 이력 관리 체계 필요. 소규모 변경은 판단 어려움
성능 모니터링 기반 재학습 — 개념
임계값은 어떻게 정하는가

초기 배포 시점의 Test 성능을 기준으로 설정합니다.

예: 배포 시 RMSE = 2.1 → 임계값 = 3.0 (50% 이상 악화 시 재학습)

또는 비즈니스 기준으로 — "수율 예측 오차가 5%p 초과하면 운영에 지장"이라면
RMSE 5 이상을 임계값으로 설정.

정답은 없습니다. 비즈니스 영향도 기준으로 정하는 게 가장 현실적입니다.

재학습 시 학습 데이터는 어떻게?

Rolling window: 항상 최근 N개월치만 사용. 오래된 데이터 제거.
→ 공정 변화 빠를 때 적합. 과거 데이터가 노이즈일 때.

Expanding window: 처음부터 누적해서 계속 추가.
→ 데이터가 많을수록 성능이 오를 때 적합. 공정이 안정적일 때.

어느 방식이 맞는지는 분석 2(Walk-forward 성능 곡선)에서 이미 확인된 패턴으로 결정합니다.

실무 권장 순서 — 처음 모델을 만들 때부터 재학습까지

Step 1 — 공정 변경 이력 확인 → 학습 데이터 시작 시점 결정
Step 2 — 예측 horizon 확인 → 최소 학습 데이터 범위 설정
Step 3 — Walk-forward로 학습 구간별 성능 비교 → 적정 범위 확정
Step 4 — 배포 후 예측 오차 모니터링 체계 구축
Step 5 — 임계값 초과 또는 공정 변경 이벤트 발생 시 재학습 트리거
Step 6 — 재학습 시 Rolling vs Expanding 중 맞는 방식으로 데이터 범위 재설정

공정 변경 이벤트

레시피 변경, 설비 교체, 원자재 로트 변경이 발생하면 데이터 분포가 급격히 달라집니다.

문제: 변경 이전 데이터로 학습한 모델이 변경 이후 예측 불가

대응: 공정 변경 이벤트를 변수로 명시적으로 추가하거나, 변경 후 데이터를 재학습 기준으로 설정

센서 이상 / 결측

제조 센서는 종종 일정 시간 동안 결측이 발생합니다.

문제: 결측 구간을 단순 보간(평균 채우기)하면 Lag 변수가 오염됨

대응: 결측 여부 자체를 변수로 추가. 결측 비율이 높은 구간은 학습에서 제외

다중 센서 시계열 동기화

센서마다 측정 주기가 다릅니다. 온도는 1분, 압력은 10초, 품질 측정은 배치 단위.

문제: 다른 주기 센서를 같은 시점으로 합치면 보간이 필요하고 이 과정에서 오류 발생

대응: 어떤 센서를 기준 주기로 쓸지, 보간 방법은 무엇인지 명시

배치 vs 연속 공정

배치 공정은 각 배치가 독립적일 수 있음. 연속 공정은 시점 간 강한 의존성.

배치 공정: 배치 내 시계열 + 배치 간 독립성 고려
연속 공정: 전형적인 시계열 분석

혼동하면 불필요한 Lag 변수 추가 또는 배치 경계 무시 오류 발생

해석 시나리오: 수율 예측 모델 — 무엇이 잘못됐는가
상황

수율 예측 모델 개발. XGBoost 사용. 학습 데이터: 2024년 전체 (1월~12월).
결과: Train R² = 0.97, Test R² = 0.95 — 우수한 성능.
배포 후 2025년 1월부터 실제 성능이 급격히 저하됨.

④ 2024년과 2025년 공정 조건이 다른가?

❌ 문제였을 경우
random split 사용 → 2024년 12월 데이터가 Train에 포함

문제 유형 A — 새 카테고리 등장

예시 시나리오: AI팀에서 아래 결과를 보고했습니다
보고 내용

모델: XGBoost
데이터: 2023~2024년 센서 데이터 (24개월)
변수: 온도, 압력, 유량, 전류, rolling_mean_7일, lag_1
검증: 80/20 random split
Train R²: 0.96 / Test R²: 0.94
결론: "높은 예측 정확도로 수율 예측 가능. 즉시 배포 추천"

여러분이 확인해야 할 것들
  • ✕
    "80/20 random split" — 시계열에 random split 사용
    24개월 데이터를 무작위로 섞었다면, 2024년 데이터가 Train에 들어가고 2023년 데이터가 Test에 들어간 상태. 미래를 보고 과거를 예측하는 구조. R² 0.94는 신뢰 불가.
  • ✕
    rolling_mean_7일 — 계산 순서 확인 필요
    전체 데이터에서 먼저 rolling을 계산한 후 split했다면, center=True가 아니더라도 split 경계 근처 데이터에서 오염 가능. 언제 rolling을 계산했는지 코드 확인 필요.
  • !
    Train R² 0.96 vs Test R² 0.94 — 차이가 너무 작을 수 있음
    일반적으로 Train이 Test보다 높은 게 정상. 차이가 0.02라면 Leakage로 인해 Test 성능이 부풀려진 것일 수 있음. 또는 모델이 충분히 복잡하지 않아 과적합이 없는 것일 수 있음 — 양쪽 가능성 모두 확인.
  • !
    2023~2024 데이터 — 공정 변경 이벤트 없었는지 확인
    2년간 레시피 변경, 설비 교체, 원자재 변경이 있었다면 초기 모델이 후기 공정을 제대로 반영 못할 수 있음.
  • ✓
    lag_1 변수 사용 — 시계열 특성을 반영하려는 시도 자체는 올바름
    다만 lag 변수 계산 시 split 이후에 했는지 확인. 올바른 lag 계산이었다면 이 변수는 유의미한 정보를 담고 있을 가능성이 높음.

핵심 질문: "시계열이면 ARIMA 써야 하나요?" — 정답은 없습니다. 어떤 문제냐에 따라 달라집니다. 판단 기준을 익히는 게 목표입니다.
시계열 전용 모델

대표: ARIMA, SARIMA, Prophet, Exponential Smoothing

핵심 원리: "과거 값의 패턴만으로 미래를 예측한다"
y 자체의 시간 구조(추세, 계절성, 자기상관)를 수식으로 모델링

입력: y 시계열 하나 (또는 소수의 외부 변수)
강점: 외부 변수 없어도 동작. 결과 해석이 직관적. 불확실성 구간 제공
약점: 외부 요인(공정 조건 변화) 반영이 제한적. 변수가 많을 때 약함

일반 ML + 시계열 피처

대표: XGBoost + Lag/Rolling 변수, LinearRegression + 시계열 피처

핵심 원리: "과거 패턴을 변수로 만들어서 일반 모델에 넣는다"
lag_1, rolling_mean_7 같은 피처를 직접 설계해서 기존 모델에 투입

입력: y의 lag/rolling + 외부 변수 (온도, 압력, 설비 조건 등) 함께
강점: 외부 요인과 시계열 패턴을 동시에 활용. 변수 많을 때 강함
약점: 피처 설계를 직접 해야 함. Leakage 위험. 불확실성 구간 없음

시계열 전용 모델 원리 — ARIMA 직관
ARIMA
AR + I + MA — 세 가지 메커니즘의 조합
과거 값, 과거 오차, 차분(differencing)을 조합해서 다음 시점을 예측합니다.

AR (AutoRegressive) — 자기 자신의 과거 값으로 예측
"오늘 온도 = 어제 온도 × 0.7 + 그제 온도 × 0.2 + 상수"
주식, 센서 신호처럼 직전 값이 다음 값에 강하게 영향을 줄 때 유효

I (Integrated) — 차분으로 추세 제거
원래 값이 계속 올라가는 추세라면 → "이번 값 - 저번 값"의 차이(변화량)로 변환
변화량은 추세 없이 일정한 범위 안에서 움직임 → 모델이 학습하기 쉬워짐

MA (Moving Average) — 과거 예측 오차로 보정
"이번 예측 오차 = 지난번 예측이 얼마나 틀렸는지 × 가중치"
갑작스러운 충격(이벤트) 이후 값을 보정하는 역할

잘 맞는 상황
y 자체의 패턴이 강하고 반복적일 때. 외부 변수 없이 순수 시계열만 있을 때.
잘 안 맞는 상황
공정 조건 변경처럼 외부 요인이 y를 결정할 때. 설명 변수가 많을 때.
일반 ML + 시계열 피처 원리 — "직접 변수를 설계한다"
ML + Lag/Rolling
시계열 패턴을 변수로 손수 만들어서 기존 모델에 투입
ARIMA가 수식으로 자동 처리하는 것을, 사람이 직접 피처로 만들어 넣는 방식입니다.

ARIMA의 AR 효과 → lag 변수로 구현: lag_1 = y(t-1), lag_2 = y(t-2)
ARIMA의 추세 효과 → rolling 통계로 구현: rolling_mean_7 = 최근 7시점 평균
그 외 → 공정 조건, 설비 상태, 시간대, 요일 등 외부 변수 함께 투입

만들어진 피처 테이블을 XGBoost, LinearRegression에 그냥 넣으면 됩니다.
모델 입장에서는 "그냥 숫자 테이블" — 시계열인지 모릅니다.

핵심 장점: 외부 변수와 시계열 패턴을 동시에 반영할 수 있습니다.
공정 온도·압력 같은 제어 가능한 변수와 과거 수율 패턴을 함께 쓸 수 있다는 게 제조 현장에서 강점입니다.

잘 맞는 상황
외부 변수(공정 조건)가 y를 강하게 설명할 때. 변수가 많을 때. 기존 ML 파이프라인 재사용 가능할 때.
주의할 것
피처 설계 실수 → Leakage. 외부 변수가 없고 순수 패턴만 있다면 ARIMA가 더 단순하고 안전.
어떤 걸 선택할지 — 판단 기준
판단 기준시계열 전용 모델 (ARIMA 등)일반 ML + 시계열 피처
외부 변수 있는가? 없거나 소수 → 적합 많을수록 → 강함
y 자체의 패턴이 강한가? 강할수록 → 적합 (자기상관 높음) 약해도 외부 변수로 보완 가능
불확실성 구간이 필요한가? 기본 제공 (신뢰구간 출력) 기본 없음 (별도 구현 필요)
공정 변경 / 이벤트 반영? 제한적 (Prophet은 일부 가능) 변수로 직접 추가 가능
해석 용이성 파라미터 의미가 명확 Feature importance로 간접 확인
데이터 양 적은 데이터에서도 동작 Lag/Rolling 피처 생성에 충분한 데이터 필요
Leakage 위험 모델 내부에서 처리 → 낮음 피처 설계 실수 → 높음
모델 선택 → 학습 범위 → 재학습 전체 흐름도
제조 현장 시나리오별 판단
시나리오추천 접근이유
"다음 시간 수율을 예측하고 싶다. 센서 20개가 있다." ML + 피처 외부 변수(센서 20개)가 많음. XGBoost + lag_1~3 + rolling 조합
"월별 생산량을 6개월 뒤까지 예측하고 싶다. 공정 데이터는 없고 생산량 이력만 있다." SARIMA / Prophet 외부 변수 없음. 월별 계절성 뚜렷. y 자체의 패턴만 사용
"설비 이상을 미리 감지하고 싶다. 진동·전류 센서 있음." ML + 피처 다변량 센서 + 이상 패턴 조합. rolling std(표준편차 급증)를 피처로 추가
"원자재 입고 수량을 예측해서 발주 최적화하고 싶다." SARIMA → ML 순서로 계절성 있으면 SARIMA 먼저. 공급사·가격 변수 추가 시 ML로 확장
현실적인 조언 — 둘 다 해보는 것이 정답

"ARIMA냐 XGBoost냐"를 이론으로 고르려 하면 막힙니다.
실무에서는 둘 다 돌려보고 성능을 비교하는 게 표준입니다.

단, 비교할 때 검증 방식은 반드시 동일하게 — 둘 다 시점 기반 split으로 평가해야 합니다.
ARIMA는 시점 기반, XGBoost는 random split으로 비교하면 XGBoost가 불공정하게 유리해집니다.

Week 6 핵심 메시지

시계열 데이터는 "행 순서에 의미가 있는 데이터"입니다.
이 특성을 무시하면 모델 성능이 과대 추정되고, 실제 배포 후 성능이 떨어집니다.

네 가지만 기억하세요:

1. 검증은 반드시 시점 기준으로 — random split은 시계열에 금지
2. Leakage는 코드 한 줄에서 발생 — Scaler, Rolling, Lag 변수 순서 확인
3. 성능 숫자보다 검증 방식을 먼저 확인 — R² 0.95도 Leakage가 있으면 무의미
4. 외부 변수 유무가 모델 선택의 첫 번째 기준 — 있으면 ML+피처, 없으면 전용 모델
